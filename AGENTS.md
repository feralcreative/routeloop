# routeloop

Multi-tenant motorcycle ride planner (TypeScript + Hono + Postgres), live in production at `routeloop.app`. Plan a multi-day ride on one map, share it by link, hand it off to Google Maps, import and export six formats.

## Architecture

Vocabulary is law: **ride > day > leg > stop/POI**. A ride is the shareable package (slug, visibility, title). A day is one day within it, a position rather than a calendar date. A leg is the routed path from point *i* to point *i+1*. Three kinds of dots: a **stop** is a point the rider means to stop at (`points.kind = 'stop'`), a **POI** is a point they will ride BY without necessarily stopping (`points.kind = 'poi'`), and **both are on the route and both anchor a leg**; a **waypoint** is an ephemeral shaping point stored as `route_legs.via_points` and never a row in `points`. "Route" means only a path, or a route *file* from another app. Not "trip", not "map".

**A day is ONE ORDERED LIST of points and `kind` is a flag on each, not a choice of which list to put it in.** Ziad's call, 2026-08-23. Every point carries `position`, both kinds, dense from 0; `day.points` in the client and the payload. **Every user-created point starts as a POI**—a map click, either search arm, a saved place—and is promoted by being given a category, or from the row menu. **The exception is the first point of a day, which is promoted on the spot and tagged `start`**, which is what keeps "at least one stop per day" true without the rider being asked.

**A POI IS PART OF THE ROUTE. `legs[i]` joins `points[i]` to `points[i+1]`, whatever kind either end is.** Ziad's call, 2026-08-24: a POI is something you will at least ride BY—an address, or a spot in the middle of nowhere—just not necessarily somewhere you stop. So `kind` touches nothing about routing and there is **one index space**: a point's position in the day IS its leg index. `stopsOf()` survives on both sides only for the surfaces that genuinely count stops—`rides.stop_count`, the roadbook's numbered rows, the Maps hand-off, and the at-least-one-stop rule—and `stopIdx()`/`stopOrdinalAt()` are gone. Three consequences to state rather than treat as bugs: **promoting a point is a free, exactly reversible flag flip** that rebuilds no leg and drops no shaping point; **adding a POI is a Routes request**, where it used to cost nothing; and **a day's leg count is bounded by `MAX_POINTS` (400), not `MAX_STOPS` (200)**.

Request path:

1. `src/index.tsx`—host middleware first, redirecting the `LEGACY_HOSTS` names 301 to the canonical host before any route or auth handler runs.
2. Static assets from `public/`, then `withSession` resolves the session once per request.
3. Route modules mounted at `/` from `src/routes/*`—see [docs/api.md](docs/api.md).
4. Gates from `src/auth/middleware.ts`: `requireAuth`/`requireAuthApi`, `requireActive`/`requireActiveApi` (`users.status`), `requireSameOrigin` (CSRF), `requireManageRiders`, `requireSurvey`.
5. Ride writes normalize and insert through `insertRideGraph` in `src/maps/ride-graph.ts`—the builder's save and the native JSON import share it, so a second path cannot drift.
6. Drizzle → Postgres. `src/db/schema.ts` is the source of truth.

Boundaries that matter:

- `public/js/map-common.js` (`window.TBMap`) is the only file that calls `google.maps`. `viewer.js` and `builder.js` go through the handles it returns and name no vendor API.
- Nine pure client helpers own arithmetic rather than DOM and are `eval`'d by their own tests: `ride-time.js`, `twist.js`, `route-shape.js`, `builder-history.js`, `duration.js`, `alts.js`, `feedback-buffer.js`, `place-query.js`, `day-clock.js`.
- `src/maps/alts.ts` is the single source of truth for what an alternate day means, mirrored by `public/js/alts.js` and pinned together by `test/alts.test.ts`. Both runtimes have to agree: the builder decides live which day is active and what the ride's mileage reads, and the server decides the same thing on save. A disagreement shows up as a builder displaying one total while the database stores another, with nothing raised.
- `src/maps/roles.ts` is the single source of truth for the 17 waypoint roles; the `waypoint_role` enum in `src/db/schema.ts`, the icons in `public/img/icons/`, and `ROLE_COLORS` in `src/maps/role-colors.ts` must all stay in sync with it. Four lists, held together by `test/roles.test.ts` and `test/role-colors.test.ts`.
- **`src/maps/role-colors.ts` is the seventeen-color categorical ring, and it deliberately does NOT follow the theme.** Seventeen categories cannot be made mutually distinguishable under dichromacy by any assignment, so shifting them with the colorblind palette would trade an honestly undifferentiable set for one that pretends otherwise. What makes the chart readable is that color is never the only cue there—every bar carries its own icon and its own text label. Generated by `utils/build-role-colors.mjs` and measured by its test; do not hand-edit a hue.
- **`test/palette-contrast.test.ts` is the contrast audit, and it compiles the SCSS to get its numbers.** All six palettes, every pair the app actually paints. It is the only thing standing between a nudged hue and an illegible theme—the values in `_palette.scss` were "reasoned rather than measured" for a week and were wrong in four places.
- `src/maps/filename.ts` is the source of truth for the export filename convention; `public/js/filename.js` mirrors it and `test/filename-client.test.ts` holds the two together. Same arrangement for `twist.ts`/`twist.js` and for `duration.ts`/`duration.js`—the last of those has a third copy to keep in step, `fmtDuration()` in `src/routes/roadbook.tsx`, which `test/duration.test.ts` also pins.
- Anything server-side that must be tested with no database is split rule-from-query: `src/invites/policy.ts` vs `service.ts`, `src/survey/score.ts` vs `questions.ts`, `src/stats/shape.ts` vs `query.ts`, `src/feedback/policy.ts` vs `service.ts`, `src/views/date-format.ts` vs `prefs.ts`.
- **`src/emails/` is pure and must stay that way.** Every module there is a function of its props and nothing else, which is what lets `test/emails.test.ts` import the whole registry with no database and no environment. Anything that reads a table to decide whether to send lives outside it—`src/auth/notify.ts` and `src/feedback/notify.ts` are the two precedents.
- **A saved place is COPIED into a ride, never referenced.** Ziad's call, 2026-08-21. There is deliberately no `place_id` on `points`: a ride is a record of what the rider planned, so renaming or deleting a place must not reach back and rewrite a ride from last year—and points churn on every save anyway, so a foreign key would have to survive that for no gain. `placeToStop()` in `src/places/policy.ts` is that decision in code, mirrored client-side by `stopFromPlace()` in `public/js/builder.js`. **The consequence to state rather than treat as a bug: fixing a badly placed pin fixes future rides only.** A place carries the DURABLE half of stop details (phone, address, links) and never the per-trip half—inheriting last September's confirmation number would be worse than having none.
- **`place_groups` deletes with `set null`, not cascade.** Deleting a group keeps its places and makes them ungrouped; `groupPlaces()` renders them in their own section. A rider tidying up a folder name must not lose their saved locations, which is exactly what cascade would do.
- **`src/images/` is the ONLY upload path that touches a rider's image, and re-encoding is not optional.** `policy.ts` is pure: it sniffs the magic number and gates on size, and it is what refuses an SVG—a document that can carry script, which served from this origin is stored XSS. `process.ts` is the sharp half and always re-encodes to WebP, because bytes reaching a server are attacker-controlled whatever the page did to them. Parameterized by a target box so #99's avatars are a caller rather than a second implementation. `test/images.test.ts` pins all of it.
- **`src/maps/compress.ts` is the only place brotli is spoken, and `readMapFile()` in `storage.ts` is the only way to read a stored original.** Callers used to build a path and `readFile()` it, which was fine while one name was possible; there are two now (`19.gpx` and `19.gpx.br`), and two places to remember a fallback is one place to forget it. Both spellings are valid on disk—a half-migrated directory works—and nothing rewrites a file lazily on read.
- **`src/trash/` is the recycle bin, and `service.ts` holds the predicates that keep it invisible.** `LIVE_RIDE`, `LIVE_PLACE` and `LIVE_PLACE_GROUP` exist so an omission shows up in review as a missing import rather than as an absent `is null`. `policy.ts` is the pure half (the 30-day hold, `trashState()`, `canRestore()`); `purge.ts` is the only code in the app that destroys a ride. Rules mirrored from `src/account/policy.ts`, deliberately: the GTFO hold on `users` is the same mechanism one level up.
- **`src/maps/point-details.ts` is the private-stop-details boundary, and it is the only module that reads `point_details`.** Confirmation numbers, gate codes and phone numbers live in their own table rather than as columns on `points` for exactly one reason: `points` is what `ride.json` is built from and what every export serializes, so a private field stored there is one forgetful `select()` away from a public share. A separate table has to be JOINed to leak, and a join is visible in review. `canSeeDetails()` is the whole rule—**owner only, and deliberately blind to `visibility`**, because sharing a route is not sharing a reservation. Details reach exactly three surfaces: the builder's own load, `ride.json` for the owner, and the native JSON. They are stripped from GPX, KML, GeoJSON and CSV, and a clone drops them (`src/routes/builder.ts`)—a public ride is clonable by anyone.
- **`visibleTo()` in `src/feedback/policy.ts` is the private-bug feature.** There is no second mechanism: a report is invisible to everyone but its author and the owner until `state = 'published'`, and nothing publishes a bug by default. `state` (the owner's gate) and `status` (the rider-facing lifecycle) are two columns for exactly this reason.
- **One third-party script loads from a CDN, on the builder only:** SortableJS 1.15.7 from jsdelivr, for drag-to-reorder, pinned with an SRI hash and `crossorigin`. Approved 2026-08-15. It is not a mistake and not leftover—but note the builder degrades rather than breaks if it fails to load, and every row menu carries Move up / Move down as both the fallback and the keyboard path. Keep both properties if you touch it. Self-hosting the webfonts was a decision about **fonts**, not a general ban on CDNs.

## Conventions

- **Coordinates are `[lng, lat]`** everywhere in this app—storage, payloads, GeoJSON, exports.
- **A button is a highway guide sign by default.** Ziad's call, 2026-08-22: `.btn` carries the green field, the inset white keyline and an arrow at the right pointing east, with no extra class. `.btn-sign` still works and means the same thing—it is an alias kept because it reads as intent. `.arrow-left` puts the arrow back on the left pointing west, and the eight `.arrow-*` bearings override the direction. **Opting out is a named list, `$btn-flat` in `style/_chrome.scss`**, and a new variant gets the sign until it is added there. That is the intended failure: a button that inherits the house style by accident is better than one that quietly leaves it.
- **A build has a version and it comes from the commit, not the deploy.** `YYYY-MM-DD-HHMMPT`—the minute of HEAD's committer date in Pacific time, e.g. `2026-08-23-1834PT`. Ziad's call, 2026-08-23. Computed by `utils/deploy/deploy.sh`, shipped as `APP_VERSION`, and read by `src/version.ts`, which falls back to `dev`. Redeploying the same tree reports the same version because it is the same code. **The `PT` is part of the value, not a label**—a bare timestamp is read in the reader's own zone, and nothing parses this string, so do not add one that does. **A new key here has to be added to the allow-list in `deploy.sh` or it reaches no environment**; `APP_VERSION` and `BUILD_SHA` are both on it.
- **Release notes are `src/content/release-notes.html`**, read through `views/content.ts` like the FAQ, and served twice: the page at `/release-notes` and the fragment at `/api/release-notes` that the modal fetches on first open. Add a release by copying the block at the top of the file. Every file in `src/content/` must also be registered in `test/content.test.ts`, which fails loudly when one is not.
- **Formatting is prettier**, configured in `.prettierrc`. Do not argue with it; note that `public/js/**` and SCSS have deliberate per-glob overrides.
- **Prose is never hard-wrapped.** One line per paragraph, soft-wrapped by the editor. Em dashes are tight (`word—word`); use a spaced en dash when a line wants air. The pre-commit hook fixes and re-stages.
- **Widows are a CSS problem first.** `text-wrap: pretty` is set on body copy in `style/_base.scss` and covers every page a browser renders, so page copy needs nothing hand-placed. Two surfaces are outside it and bind their own last two words with `&nbsp;`: `src/emails/`, because no mail client supports the property, and the printed roadbook. In static JSX write the entity straight into the markup—esbuild decodes it to U+00A0 while transpiling. For a string shared between an email's HTML and text arms, use `noWidow()` from `src/views/widow.ts`, so only the HTML arm carries the character; a text/plain part must not.
- **Views are Hono JSX** (`jsxImportSource: hono/jsx`, no React, no bundler). JSX escapes by default; `raw()` is the opt-out.
- **Tests are Vitest under `test/`**, named `*.test.ts`, pure logic only.
- **Schema changes ship as generated migrations** committed alongside the `schema.ts` change—SQL and `drizzle/meta/` both.
- **Branches** are `type/kebab-subject`; commits are Conventional Commits.

## Gotchas

Things an agent gets wrong by default. This section is why the file exists.

- **A document that disagrees with the code loses.** That has happened repeatedly here and has already caused a GitHub issue to be filed for finished work. Look at the files before believing any checklist.
- **`[lng, lat]` vs `{lat, lng}`.** Only `google.maps` speaks `{lat, lng}`, and exactly two places convert: `toLatLng`/`fromLatLng` in `public/js/map-common.js`, and `toGoogleWaypoint` in `src/routes/routing.ts`. A transposed pair still renders, just in the wrong hemisphere. GeoJSON agrees with us—do not "fix" it. Pinned by `test/round-trip.test.ts`.
- **Only active days count, and there is no single place that enforces it.** `rideTotals()` covers the stored caches, `loadRideForExport()` covers every lossy export and the roadbook and the hand-off page, five predicates in `src/stats/query.ts` cover the dashboard, and `ride-time.js` and the builder's own readout cover the two clients. A new surface that sums days has to opt in. `loadNativeRide()` and `loadRidePayload()` deliberately do the opposite and keep every day—they are the lossless paths.
- **`ride-time.js` skips losing alternates INSIDE the module, never by filtering the array at a call site.** `activeAtMoment()` returns `dayIndex`, which both clients feed straight back into `state.days[i]` and `setLegHighlight(map, i, …)`. Hand it a filtered array and every index past the first ghost is off by one, silently, and the map highlights the wrong road. **The same trap one level down is why it returns `pointIndex` and not the old `stopIndex`/`poiIndex` pair**: those indexed their own filtered arrays, so a caller holding the ordered list had to filter it the same way to read the answer.
- **`daySchedule()` is a plain walk and must stay one.** Dwell at `points[i]`, ride `legs[i]`, dwell at `points[i+1]`. It used to project every POI onto the day's concatenated track, sort by that distance, and cut the leg a POI landed inside at the right fraction—with the distances passed in by the caller as `poiDistsM`, because a builder POI has no stored `distFromStartMi` until it is saved. All of that existed only because a POI anchored no leg. Do not bring any of it back.
- **`points.uid` is the point's identity; `points.id` is not.** The builder's `PUT` deletes and re-inserts every day and point on every save, so ids churn constantly—that was accepted deliberately on 2026-08-15 and has not changed. Anything that must reference a point across a save uses `uid`, which the CLIENT mints (`uid()` in `public/js/builder.js`, mirroring `newUid()` in `src/maps/uid.ts`—same alphabet and length, or the save 400s). **There are two places points are inserted and both must supply a uid:** `insertRideGraph` and the lossy import in `src/routes/maps.ts`. A missing one fails the NOT NULL at runtime with nothing useful to say.
- **`point_details` cascades from `rides`, not from `days`.** That is what makes a stop's confirmation number survive the `delete(days)` at the top of every save. The flip side: nothing else cleans it up, so `writePointDetails` in `ride-graph.ts` deletes rows whose uid left the payload. Skip that and a deleted stop's gate code lives forever.
- **Autocomplete and Text Search answer different questions, and only one of them can answer a category.** Autocomplete matches NAMES and ADDRESSES: asked for "gas station in oakdale ca" it returns the businesses literally called that, which in Oakdale is one, while the ARCO and the Shell go unmentioned. Enumerating a KIND of place is Text Search, a different endpoint on a pricier SKU, proxied at `/api/places/search` and cached for that reason. `place-query.js` decides which question was asked and is deliberately conservative—"Shell" and "Chevron" are names, not categories, so they never spend a Text Search call. **Text Search reads "X in Y" itself**, so the place is never geocoded separately; `near` is only for a category chip, which has no place in its text.
- **The two Google keys need different API lists, and the failure is a 403 that looks like an outage.** `GMAPS_SERVER_KEY` must carry Places API (New) or every Text Search comes back `403 API_KEY_SERVICE_BLOCKED`—a console change, not a code problem, which is why the route detects that exact reason and returns a 503 naming it. The browser key already has Places because the Autocomplete uses it, so having one working search and one broken one is the expected symptom of forgetting.
- **A CATEGORY IS A REASON TO STOP: picking one promotes a point, clearing the last one demotes it.** Ziad's call, 2026-08-24. Tagging a point Gas already says you mean to be there, so requiring "make this a stop" afterwards was two actions for one intention. Three consequences: **a point created with roles arrives as a stop**, which is every category-chip result, every category query and every saved place filed under one; **demoting clears the roles**, or a POI would sit there tagged Gas and anything re-deriving one from the other would promote it straight back; and **untagging the day's only stop is refused**, because the day would have none and `payload()` drops such a day whole. The row menu keeps both items for what a category cannot say—a stop with no reason given, which imports and the first-point rule both produce.
- **It is an INTERACTION rule, not a schema one.** `points.kind` stays its own column and an untagged stop is a real, valid shape; nothing derives `kind` from `roles` on the server. Do not "simplify" it into a computed field—the importer writes untagged stops and so does the auto-promoted first point of every day.
- **The category picker's open state lives in `state.rolesOpen`, not in the DOM.** Picking a category changes the kind, which renumbers every stop below it, so the row has to be re-rendered—and a picker whose openness was only a `hidden` attribute slammed shut after every tap. Same reasoning as `state.insertAt` for the insert-between rows; both are cleared by `renderDays()` because a delete or a reorder shifts the indices they are expressed in.
- **`poi` is BOTH a role and a kind, and they mean nearly opposite things.** The kind is somewhere you ride past; the role is somewhere you stop to look at something. The role is labeled **Sight** on every rider-facing surface for exactly this reason and keeps the identifier `poi` in code, the `waypoint_role` enum and `ROLE_META`—renaming the enum value is a migration over every stored point. Do not "fix" the label back.
- **The date format members are real locale tags, and that is what makes the CLOCK follow.** `src/views/date-format.ts` stores `en-US` / `en-GB` / `en-CA` rather than an abstract `mdy`/`dmy`/`ymd`, so Intl decides the digit order, the 12-vs-24-hour clock and the padding together—a British rider gets `24/08/2026` AND `16:00`. `fmtClock` uses `timeStyle: 'short'` for the same reason: spelling out `hour`/`minute` imposed our padding on every locale. Adding a locale is one enum member and no formatter changes.
- **Number grouping is still hardcoded `en-US` in `src/stats/shape.ts`, on purpose.** All three date-format members are English and group identically as `1,234`, so threading a format through ten `fmtMiles`/`fmtCount` call sites would change nothing anyone can see. `fmtNumber` in date-format.ts exists for the day a member like `de-DE` (`1.234`) lands.
- **`user_profiles` rows are created LAZILY, by the settings upsert.** So most riders have no row, which is what lets `dateFormatFor` fall through to `Accept-Language` and give a German browser day-first without anyone choosing. The consequence: an upsert that creates a row to save some OTHER preference must seed `date_format` from the header on INSERT and leave it out of the update set, or saving a duration preference silently stamps `en-US` over what the header was already giving them. Both handlers in `settings.tsx` do this; a third one has to as well.
- **`null` is not zero.** Twistiness `null` means nothing measured it; `0` means the road is straight. Same for `dist_from_start_m` on a trackless import. A format that guesses is indistinguishable from one that knows.
- **`dist_from_start_m` is the prefix sum of the legs before a point, for BOTH kinds.** There used to be two algorithms split by kind—a prefix for stops, a nearest-vertex projection onto the concatenated track for POIs, because a POI had no leg boundary of its own. Every point has one now, so the prefix is the answer for all of them: exact rather than approximate, and never null on a day that has legs. `distFromStartAlongTrack()` survives for the lossy import path only, where a GPX waypoint arrives with no position and the track is the only thing that can place it.
- **`rides.size_bytes` must name every byte column.** The app increments `users.used_bytes` on import and the database decrements it from `size_bytes` on delete, so a column missing from that generated expression leaks quota on every delete, silently. **No longer permanently, as of 2026-08-24:** `src/account/quota-sweep.ts` rewrites every rider's tally from `sum(rides.size_bytes)` every five minutes, so a drift now has a five-minute life rather than an unbounded one. That is a safety net and not a licence—the sweep repairs the tally FROM the generated expression, so a byte column missing from it is still invisible to both.
- **A BIKE'S RANGE IS STORED IN METERS AND TYPED IN MILES, and `src/bikes/policy.ts` is the only place they meet.** `METERS_PER_MILE` is that boundary; above it everything is miles because that is what the form asks for, below it everything is meters because #150 will switch the site to metric and a value stored in whatever unit someone typed drifts on every round trip. A mile reaching the meters column reads as a bike that can go 290 where the rider said 180.
- **A form must never advertise a maximum the database rejects.** `MAX_RANGE_MILES` floors rather than using `metersToMiles`, which rounds: 2,000,000 m rounds UP to 1,243 mi, and 1,243 mi converts back past `ck_bike_range`. The rider would have got a 500 for entering exactly the number they were told was allowed.
- **`sharp` sets orientation with `withMetadata({orientation})`, NOT `withExif({IFD0:{Orientation}})`.** The second spelling writes a tag sharp reads back as 1, so a test fixture built that way is not sideways and the test passes for the wrong reason. `.rotate()` must also come FIRST in the pipeline: sharp writes no metadata to its output, so rotating later would drop the tag while leaving the pixels on their side.
- **A bike photo is `bike-<id>.webp` in the owner directory, and it deliberately does NOT parse as a stored ride original.** `parseStoredName()` needs a leading digit, so `listOwnerFiles()`, the account archive and `deleteMapFiles()` all skip it while `deleteOwnerDir()` still takes it on account purge. `photo_bytes` is counted on `bikes` and NOWHERE else—never in `users.used_bytes`, exactly as `feedback_attachments` does it.
- **`.br` HAS TO BE IN THE FILENAME BECAUSE BROTLI HAS NO MAGIC BYTES.** Gzip starts `1f 8b` and could be sniffed out of a file still called `19.gpx`; brotli cannot be identified from its bytes at all. That is why the suffix is load-bearing rather than cosmetic, and why `parseStoredName` captures it and `StoredFile` carries `compressed`. `.br` must never join `STORED_EXTS`—that list is the closed set of RIDER-supplied extensions the containment check leans on, and the suffix is ours.
- **`rides.size_bytes` NO LONGER DESCRIBES BYTES ON DISK.** The byte columns keep meaning the size of the original as the rider uploaded it, because an allowance must not depend on how well someone's file happened to zip. Disk holds roughly a fourteenth of that. "How much disk are we using" is a `du`, not a query, and there is deliberately no second column—`size_bytes` means one thing.
- **The account archive must DECOMPRESS on the way in, and this is the sharp edge of the whole compression change.** Its zip entries are named `.gpx`; putting brotli bytes under that name hands a rider a backup that silently will not open, and nothing anywhere would raise it. `src/account/export.ts` goes through `readMapFile()` for exactly this reason.
- **`ALTER COLUMN ... SET DEFAULT` reaches new rows only, so a changed default needs a hand-written `UPDATE` beside it.** `drizzle/0012` is the worked example: the differ emitted the `SET DEFAULT` for the 100 MB quota and nothing else, which would have raised the allowance for riders who do not exist yet and left every current one at 25 MB. Scope the UPDATE to rows still holding the OLD default, or a quota somebody set by hand is silently discarded.
- **THE `deleted_at is null` IN `reconcileUsedBytes()` IS LOAD-BEARING.** Trashing a ride frees its quota on the spot while the row and its files stay for thirty days. Drop that predicate and the five-minute quota sweep adds the bytes straight back—the rider watches their meter fall and then silently rise, and every trash is undone as far as the allowance is concerned. Nothing raises anything.
- **`uq_place_group_name` is PARTIAL, which breaks a bare `ON CONFLICT`.** Binning a group frees its name immediately (`where deleted_at is null`), and Postgres cannot infer a partial unique index from a column list alone—`createGroup()` must restate the predicate via drizzle's `where` option or the insert fails outright with "no unique or exclusion constraint matching". There is no type error and no test: places have no database-backed tests, so it surfaces as a 500 on "create a group".
- **A purge removes FILES FIRST and the row SECOND**, which is the opposite of what the old hard delete did and is not a mistake. Row-first leaves orphaned files if the process dies between the two, because the row that named them is gone. Files-first leaves a claimed row whose files are already removed, and the stale-claim reclaim (`CLAIM_STALE_MS`) finishes it. `deleteMapFiles` is idempotent, so the retry costs nothing.
- **A claim column has to expire or it strands the row it was protecting.** `purge_started_at` stops two sweeps purging the same row at once; without the stale reclaim, a process that dies mid-purge leaves that row claimed forever, never re-selected and half-destroyed.
- **The account purge had no runner at all until 2026-08-26.** `/account/delete` stamped `purge_after`, locked the rider out and showed them a destruction date, and nothing destroyed anything—`src/account/purge.ts` did not exist although `policy.ts` referred to it. It is now gated behind `PURGE_ACCOUNTS` precisely because its first pass will find everyone who has been overdue for however long that was.
- **`.tb-marker` is deliberately `0×0`** in `style/_map.scss`. An `AdvancedMarkerElement` anchors its content at bottom-center, so a zero-size wrapper puts the anchor on the point and the negative-margin offsets keep working. Give it a size and every marker drifts.
- **A day is drawn as one polyline**, the concatenated geometry of all its legs, with the duplicate vertex dropped at each joint and no indices consumed by an empty leg. Turning a drag index back into a leg plus a via-point slot is the entire job of `public/js/route-shape.js`. Do not switch to one polyline per leg—the layer-id contract every caller depends on assumes otherwise.
- **Two points in the same place get a zero-length `[v, v]` leg, not a one-coordinate one.** `legSchema.geometry` requires two, and duplicating a point deliberately puts the copy on top of its original. This is also how `splitDayTrack` handles a track with fewer vertices than points, which is what replaced the old demote-the-overflow-to-POIs mechanism—demotion freed a vertex only while a POI consumed none.
- **The zip download route is registered ahead of the generic `:format` route on purpose** in `src/index.tsx`. Registered after it, the generic route swallows `/zip/gpx` and answers with a plain GPX. Observed, not theorized.
- **The `routeloop_` filename marker is load-bearing.** `parseExportName` returns `null` without it, so a rider's own `day-2.gpx` is never reinterpreted. Underscores separate fields and hyphens live inside one; do not simplify the separator. Dates are formatted and parsed in UTC because the roadbook renders `days.start_at` with `timeZone: 'UTC'`.
- **Two brand names are read where one is written, and that is permanent.** `READ_MARKERS` in `src/maps/filename.ts` accepts `tankbag_` alongside `routeloop_`, `COMPOUND_EXTS` accepts `.tankbag.json`, `nativeVersion()` in `src/maps/export.ts` reads either version key, and `/api/public/maps/:slug/tankbag.json` is still routed. None of that is leftover debris from the rename—it is what keeps every file a rider already downloaded importable, and dropping it fails silently: the files still import, just stripped of the day order and dates that GPX and KML cannot carry internally. `public/js/filename.js` mirrors all of it. Tidying any of it away needs a decision, not a cleanup pass.
- **A filename is not a format.** It carries four fields and the date is the one doing the work, because GPX and KML cannot hold a schedule. Resist adding roles, colors or dwell to it.
- **The pre-commit tightener rewrites em dashes in test fixtures too.** `test/em-dashes.test.ts` was once committed comparing strings to themselves because of it.
- **A COLOR TOKEN IS A `var()` NOW, AND ANYTHING THAT READS THE SCSS TO FIND A COLOR IS BROKEN BY THAT.** `/brand` parses `_tokens.scss` and decides "is this a color" with a regex, and the theme engine turned every token in that file into `var(--x)`—so the page went from every color the app defines to none of them, on a branch whose entire subject was color, and nothing failed. The values live in the compiled stylesheet; `parsePalette()` in `src/views/tokens.ts` reads them back out of the `:root` block. Reading the BUILD rather than re-deriving the palette in TypeScript is deliberate: a second implementation of the color math would disagree eventually, and the disagreement would look like a design decision.
- **`ul.cards` is the generic white-row list; `.ride-cards` is the ride grid.** They are two classes because they are two things—`/admin`'s rider roster and the survey summary are built on the first, and turning it into a picture grid gave the roster a column of empty frames. A ride list wants `.ride-cards`, with `.ride-cards--dense` where the list is not the page's whole job.
- **`contrast()` in `src/views/tokens.ts` must read `rgb()` as well as hex.** Sass emits a hex for an authored literal but `rgb(60%, 40.47%, 0%)` for anything `color.adjust()` produced, which is every derived token in the palette—so a hex-only reader silently skips exactly the tokens most likely to have a contrast problem. It also knows `black` and `white`, because Sass writes the shortest form and a derivation clamped at either end of the lightness scale arrives as a keyword.
- **`color.adjust()` does not clamp at zero.** Darkening a color past its own lightness emits `hsl(…, -3.04%)`, which is out of range, which a browser clamps to black—so the token silently resolves to black and the build succeeds. `-adj()` in `_palette.scss` clamps for that reason.
- **A derivation whose job is to be READ takes an absolute lightness, not a relative step.** A step assumes the base sits where the default palette put it, and a theme that moves the base moves the step with it: the high-contrast theme lightened `$warning`, correctly, because it is a black-legend field—and `$pending`, which was `-20%` from it, came out at **2.24:1 on white**. Amber text was least legible in the theme named for legibility. `-tone()` is the fix.
- **There is no global `border-box` reset in `style/`.** Every fixed-size box sets its own `box-sizing`, so a new one that forgets has its `width` and `aspect-ratio` describe the CONTENT box while padding sits outside them—it renders wider than it declares and nothing warns. It cost a day on `.btn-stop`, where the symptom was a legend that would not wrap at any viewport.
- **Never put a raw U+00A0 in source.** It is invisible in a diff and in most editors, so a stray one is unreviewable and a stripped one is undetectable. Write `&nbsp;` in JSX text, `'\u00a0'` in a string literal. Note also that the em-dash tightener counts a non-breaking space as whitespace on both sides of a dash, so binding a pair across an em dash is silently undone by the pre-commit hook.
- **A broad `npx prettier --write "src/**/*.ts"` produces about 22 files of collateral.** The committed tree is not prettier-clean under the current config, so a wide glob reformats files you never touched—line wraps collapsed, arrow-body parens added—and sweeps them into your commit. Scope the glob to the files you actually changed.
- **Never interpolate a JS array into a tagged `sql` template.** Drizzle expands the array into a tuple, so a hand-written `= any(...)` over one comes out as `any(($2, $3, $4))`, which is not valid SQL. Use `inArray`. There is no type error and no test failure—it fails at runtime, on the first render of whatever page needed it.
- **An email may not put `#` before a number.** `test/email-theme.test.ts` scans rendered HTML for `#` followed by 3–6 hex characters to catch a template inventing a color, and every decimal digit is also a hex digit, so "Report #1042" fails the guard. The scanner cannot be narrowed to attribute values either: `shell.tsx` puts most colors in `<style>` blocks. Write "Report 1042".
- **`test/emails.test.ts` requires every link in a template's HTML arm to appear in its text arm.** A text-only client silently losing a link is the failure the two-arm contract exists to prevent.
- **Feedback attachment bytes are counted in `feedback_attachments.bytes` and nowhere else.** They must stay out of `rides.size_bytes` and `users.used_bytes`—an attachment is not ride data, must not eat a rider's quota, and a fourth byte column in that generated expression would corrupt quota accounting on every ride delete.
- **The queue's moderation handler writes only the fields it is given.** That is why it is several small forms rather than one wide one: a single form carrying every field would blank whatever the owner had not retyped. Keep `moderate()` field-optional if you touch it.
- **`utils/` is not in `tsconfig.json`.** `npm run typecheck` does not cover it, and a bad import there fails only at runtime. Check a `utils/` change by hand:

  ```bash
  npx tsc --noEmit --strict --target ES2022 --module ESNext --moduleResolution Bundler \
    --types node --esModuleInterop --skipLibCheck utils/seed-demo-rides.ts
  ```

- **`test/` is in `tsconfig.json` on purpose.** Vitest transpiles without type-checking, so removing it hides fixture drift. Keep it there.
- **The builder's snapshot shares what is never mutated in place, and that set changes.** `leg.geometry` is shared by reference because it is always replaced wholesale; `point.roles` must be copied because `splice()` mutates it, and `point.details` joins it for the same reason—the field editor assigns into that object one field at a time, and `details.links` is an array it pushes to. `leg.viaPoints` moved between the two groups the day drag-to-shape shipped and nothing failed loudly. Re-check whenever you add an edit-in-place feature.
- **SortableJS `filter` cancels the click that focuses an input, and `preventOnFilter: false` is what stops it.** The option defaults to TRUE, so Sortable calls `preventDefault()` on any pointerdown landing inside a filtered element—and the default action being canceled is the one that moves focus. Each day's `.add-row` is filtered so a drag cannot start on it, which silently made its search field unclickable: it could be tabbed to and typed in, but a click left focus on `<body>`. Shipped that way and reported as "I can't click into the search"; fixed 2026-08-22. `filter` still blocks the drag either way—that check does not need the event canceled.
- **Empty days are dropped at save time.** The API requires at least one stop per day, so `payload()` in `builder.js` filters days with no points rather than failing the whole ride. The stop is guaranteed by `addPoint()` promoting the first point of every day; the schema still refuses a day of nothing but POIs, and the refine says so. Note the rule is no longer about routing—a day of nothing but POIs draws a complete road—but about the roadbook's numbered rows, the Maps hand-off, and somewhere for `start`/`finish` to live.
- **`ride.json` sends ONE ordered `points` array, the same shape as the builder payload and the native JSON.** It sent `stops` and `pois` as two arrays until 2026-08-24, deliberately, because the viewer draws markers and a timeline and never rendered points as a sequence. A POI joining the route ended that: `ride-time.js` walks the points and the legs together to build a day's schedule, and two arrays cannot tell it the order. `ride-time.js` and `twist.js` are shared by the builder and the viewer and now accept ONE shape—do not reintroduce a second, or the two surfaces will disagree about a ride's schedule.
- **Native JSON is format version 5, and versions 2, 3 and 4 still import.** `upgradeNativeRide` merges a pre-v4 file's `stops` and `pois` into one list, stops first, stamping each kind explicitly—a v3 stop must not fall through to the `poi` default. **v5 is the first bump that is not a rename:** a pre-v5 file holds `stops - 1` legs where a day now needs `points - 1`, so every day's legs are re-cut from its own track at every point (`relegDay` in `track-split.ts`) and the recorded riding time is spread across them by distance rather than zeroed. Nothing is re-routed and no coordinate is invented. The rider's ORDER is kept rather than re-derived—a v4 POI's place in the list was their own choice, so a point projecting behind its predecessor is clamped forward for a zero-length leg instead of being sorted. Riders have those files on disk and a backup that will not restore is not a backup.
- **The production database is precious, and the uptime is no longer free.** Three riders have had accounts on production since 2026-08-25, so a broken deploy is now visible to somebody rather than to nobody—that half of this rule changed, and the app is still not zero-downtime ([docs/zero-downtime-deploy.md](docs/zero-downtime-deploy.md) is a proposal, not a record, and `post-deploy.sh` still runs migrations after the container is serving). Overwritten code costs approximately nothing, because the tree is in git. The rows are the opposite: `users` holds real outside signups, some active and some sitting at `status = 'pending'`, and those records are not reconstructable. Take a `db-backup` before anything that could touch the volume, and treat `docker compose down -v`, a `$DOMAIN` change, and a stale-volume adoption as the three ways to lose them. Nothing in the app prunes a pending user, so the only risk is operational.
- **A DAY'S CLOCK IS A WALL CLOCK AT THE DEPARTURE POINT, CARRIED AS UTC.** Ziad's call, 2026-08-24: a time is a time is a time at the departure point. A rider who plans a 9am departure means 9am where the bike is—whether they planned it from home, from a hotel two states over, or from London a fortnight before flying out—so **nothing in this app converts a day's clock into anyone's local time, ever**. `public/js/day-clock.js` is the only place the conversion between that value and an `<input type="datetime-local">` happens, and `point_details.check_in_at`/`check_out_at` follow the same rule. Three consequences to state rather than treat as bugs: **the columns stay `timestamptz` although the values are naive**, because node-postgres parses a real `timestamp` in the PROCESS's zone and the app would then depend on `TZ` (measured, not assumed—a stored `09:00` reads back `16:00Z` on a Pacific machine); **every surface reads it with `timeZone: 'UTC'`**, which is now correct rather than the workaround it was; and **a rider in London planning a California ride types California times**, because the field has no zone of its own to show them. Do not "fix" the UTC away.
- **Be careful with how a migration runs, not about whether to do one.** Deferring a schema change out of caution once shipped imports that destroyed multi-day structure.
- **A data migration is not always a SQL file, and the ones that are not fail silently.** The 2026-08-24 leg-count change needed no schema change at all—`route_legs` never referenced a stop—so nothing rejects a day still carrying `stops - 1` legs. Opening one in the builder fills the gap with straight placeholder legs drawn out to each POI and back, on the first edit, with nothing raised. `utils/split-imported-legs.ts` is the fix and it has to be RUN; `--dry-run` first, and a `db-backup` before it either way. **The wall-clock change the same day is the second of these**: nothing rejects a `start_at` still holding an instant, it just prints hours out, and `utils/shift-days-to-wall-clock.ts --zone <IANA>` un-applies the offset. That one is **not idempotent**—a shifted row is indistinguishable from an unshifted one—so it runs once, after a backup.

## Commit and PR conventions

- **An audible gets its issue written AFTER the fact, and closed immediately.** Ziad's call, 2026-08-24. Work here is often raised out loud and built the same day, and stopping to file a ticket first is exactly the friction that makes it not happen—so the issue is written when the work is done, describing what was decided and why, and closed in the same breath. **It is not optional bookkeeping**: the tracker is what answers "why is it like this" a year from now, and twenty-three issues had to be reconstructed on 2026-08-24 because nobody had been doing it. One issue per coherent unit of work, labeled as if it had been filed up front.
- Conventional Commits: `type(scope): subject`, imperative mood. Types in use: `feat`, `fix`, `refactor`, `docs`, `chore`, `style`, `test`. Scope optional, welcome when it clarifies.
- Branch as `type/kebab-subject`—`feat/trip-timeline-slider`, `fix/multi-track-import`.
- **BRANCH BY AREA, NOT BY ISSUE, AND PREFER FEWER LARGER PRs.** Ziad's call, 2026-08-24. Every issue carries exactly one `area:` label (a few carry two where the work genuinely straddles), and an area is the unit of work: pick one, branch, clear what you can of `gh issue list --label area:<name>`, open one PR, move on. **Group liberally**—a hyper-granular history of one-issue branches is explicitly not wanted. The nine areas, and the open count as of 2026-08-24:

  | Area | Open | What it covers |
  | --- | --- | --- |
  | `area:builder` | 15 | The builder page, its panel, stop and point handling, and routing preferences |
  | `area:schema` | 11 | `src/db/schema.ts` and the rider/group layer—friendships, membership, subgroups, voting |
  | `area:ops` | 5 | Config, deploy, CI, infra, and the feedback subsystem |
  | `area:dashboard` | 5 | The dashboard at `/`—`home.tsx`, `dashboard.js`, `_dashboard.scss` |
  | `area:import-export` | 4 | `kml.ts`, `export.ts`, `maps.ts`, and the `/import` page's format work |
  | `area:viewer` | 3 | `viewer.js`, the timeline, the navigate page, and the roadbook |
  | `area:account` | 3 | Profile, preferences, and the account pages—`account.tsx`, `settings.tsx`, `/prefs` |
  | `area:chrome` | 2 | Site-wide layout, styling, and shared components—`_chrome.scss`, `layout.tsx`, themes |
  | `area:map-engine` | 1 | `map-common.js`, `expand.ts`, `gmaps-links.ts`—the load-bearing `google.maps` boundary |

  **Two folds were deliberate and are not gaps to fill later:** routing options live in `area:builder` rather than an `area:routing` of their own, and the whole rider/group layer lives in `area:schema` rather than an `area:riders`. Both were split out and then folded back the same day, because fewer branches beat a truer taxonomy.
- Hand over a single chained one-liner (`git add -A && git commit -m "…"`) and let Ziad run it. Do not commit unasked.
- Before opening a PR: `npm run typecheck`, `npm test`, and `npm run sass` if SCSS changed. Link the issue it closes. A fix for something the tests missed should come with the test that would have caught it.
- Never commit: `.env`, compiled CSS, `storage/`, `_PLANS/`, database dumps.
