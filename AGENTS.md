# routeloop

Multi-tenant motorcycle ride planner (TypeScript + Hono + Postgres), live in production at `routeloop.app`. Plan a multi-day ride on one map, share it by link, hand it off to Google Maps, import and export six formats.

## Prohibitions

- **Never commit, push or deploy without being asked.** Deploys go to a live site riders have accounts on.
- **Never add AI attribution** to a commit message or PR body—no `Co-Authored-By`, no generated-with footer.
- **Never hand-edit:** `public/style/main.min.css` (run `npm run sass`), `drizzle/*.sql` after it has been applied anywhere, `drizzle/meta/` (written by `db:generate`), `package-lock.json` (`npm install`).
- **Never add new SQL to `utils/deploy/sql/`.** Those dated files are the `push`-era record of what ran against production and stay as history. New schema work goes through `npm run db:generate` into `drizzle/`.
- **Never lint or compile SCSS through an IDE extension.** `npm run sass`, and fix lint findings in code rather than with a CLI autofixer.
- **Never read `.env`, `storage/`, `_PLANS/` or any `*.sql.gz` into a commit, a log or a chat response.** All are gitignored and hold credentials, rider files or database dumps.
- **Read the generated SQL before applying a migration**, and rewrite it when the differ guessed wrong. A rename comes out as a drop plus an add; a `NOT NULL` on a populated column needs a backfill ahead of it. Riders hold data that cannot be rebuilt from an upload.
- **EVERY MIGRATION MUST BE RUNNABLE AGAINST THE RELEASE THAT PRECEDES IT. Expand/contract only; a rename is two deploys.** Ziad's call, 2026-08-27, and it is the price of blue/green: from the moment `migrate` finishes until the old color drains, roughly 30–60 seconds, **the OLD code is serving against the NEW schema**. Safe in one deploy: a nullable column or one with a default, a new table, an index, an enum value, a widened type, a relaxed constraint. Never safe in one deploy: dropping a column or table the previous release still writes, renaming anything, a `NOT NULL` with no default on a column the old code does not write, or tightening a `CHECK`/adding a `UNIQUE` the old code can violate. A rename becomes: deploy one adds the column and dual-writes, deploy two drops the old one. **`--no-overlap` on the deploy is the escape hatch** and it stops the old color before starting the new one, so a genuine emergency is never blocked—it just costs one deploy with real downtime. **The consequence to state rather than treat as a bug: a failed health gate leaves the schema AHEAD of the serving code**, migrations having already run against a color that never took traffic. That is survivable exactly and only because of this rule, which is why it is here rather than in a guideline.
- **Human approval required** for: any schema change, any new dependency, anything touching prod or stage, and removing the `map-common.js` boundary.

## Architecture

Vocabulary is law: **ride > day > leg > stop/POI**. A ride is the shareable package (slug, visibility, title). A day is one day within it, a position rather than a calendar date. A leg is the routed path from point *i* to point *i+1*. Three kinds of dots: a **stop** is a point the rider means to stop at (`points.kind = 'stop'`), a **POI** is a point they will ride BY without necessarily stopping (`points.kind = 'poi'`), and **both are on the route and both anchor a leg**; a **waypoint** is an ephemeral shaping point stored as `route_legs.via_points` and never a row in `points`. "Route" means only a path, or a route *file* from another app. Not "trip", not "map".

**A day is ONE ORDERED LIST of points and `kind` is a flag on each, not a choice of which list to put it in.** Ziad's call, 2026-08-23. Every point carries `position`, both kinds, dense from 0; `day.points` in the client and the payload. **Every user-created point starts as a POI**—a map click, either search arm, a saved place—and is promoted by being given a category, or from the row menu. **The exception is the first point of a day, which is promoted on the spot and tagged `start`**, which is what keeps "at least one stop per day" true without the rider being asked.

**A POI IS PART OF THE ROUTE. `legs[i]` joins `points[i]` to `points[i+1]`, whatever kind either end is.** Ziad's call, 2026-08-24: a POI is something you will at least ride BY—an address, or a spot in the middle of nowhere—just not necessarily somewhere you stop. So `kind` touches nothing about routing and there is **one index space**: a point's position in the day IS its leg index. `stopsOf()` survives on both sides only for the surfaces that genuinely count stops—`rides.stop_count`, the roadbook's numbered rows, the Maps hand-off, and the at-least-one-stop rule—and `stopIdx()`/`stopOrdinalAt()` are gone. Three consequences to state rather than treat as bugs: **promoting a point is a free, exactly reversible flag flip** that rebuilds no leg and drops no shaping point; **adding a POI is a Routes request**, where it used to cost nothing; and **a day's leg count is bounded by `MAX_POINTS` (400), not `MAX_STOPS` (200)**.

Request path:

1. `src/index.tsx`—host middleware first, redirecting the `LEGACY_HOSTS` names 301 to the canonical host before any route or auth handler runs.
2. Static assets from `public/`, then `withSession` resolves the session once per request.
3. Route modules mounted at `/` from `src/routes/*`—see [docs/api.md](docs/api.md).
4. Gates from `src/auth/middleware.ts`: `requireAuth`/`requireAuthApi`, `requireActive`/`requireActiveApi` (`users.status`), `requireSameOrigin` (CSRF), `requireManageRiders`, `requireSurvey`.
5. Ride writes normalize and insert through `insertRideGraph` in `src/maps/ride-graph.ts`—the builder's save and the native JSON import share it, so a second path cannot drift.
6. Drizzle → Postgres. `src/db/schema.ts` is the source of truth.

Boundaries that matter:

- `public/js/map-common.js` (`window.TBMap`) is the only file that calls `google.maps`. `viewer.js` and `builder.js` go through the handles it returns and name no vendor API.
- Fourteen pure client helpers own arithmetic rather than DOM and are `eval`'d by their own tests: `ride-time.js`, `twist.js`, `route-shape.js`, `builder-history.js`, `duration.js`, `alts.js`, `feedback-buffer.js`, `place-query.js`, `day-clock.js`, `drag-index.js`, `day-distance.js`, `day-split.js`, `corridor.js`, `range-circle.js`. `drag-index.js` is four lines of clamping that lived inside a Sortable `onEnd` closure until #166, where no test could reach it—**a helper exists so the arithmetic is reachable, and moving it out is the fix, not a tidy-up.**
- **A SUBGROUP'S APPROACH IS A DAY, NOT A SET OF LEGS.** Ziad's call, 2026-08-26, settled before #67 was built because #67 asks for it to be. `days.subgroup_id` nullable; null means everyone rides it. A subgroup owns a SUBSEQUENCE of the ride's dense positions, so `uq_day_ride_pos` never changed and a multi-day approach is simply more days. The rejected model—subgroups on legs—reads better in the issue and breaks the settled rule that a day is ONE ORDERED LIST of points: two feeders cannot both start at position 0 of one list. See docs/decisions.md before reopening it.
- **A MEET AND A SPLIT ARE DERIVED, NEVER STORED.** `junctions()` in `src/subgroups/policy.ts` walks the day list; a run of tagged days followed by a shared one is a meet, the reverse is a split. Nothing needs a column, and the `meet`/`split` waypoint roles stay exactly what they were—a label a rider or an importer puts on a point, which nothing reads structurally. Deriving beats storing because the shape changes every time a day is added, removed or reordered, and a stored flag would be wrong the first time anybody dragged one.
- **`src/subgroups/schedule.ts` keeps WHOSE clock and WHICH event as two separate axes**, `rides.primary_subgroup_id` and `rides.time_anchor`. That is what dissolves the contradiction #143 was written with—one group setting the departure while another is pinned at 9am is two anchors, and only one can hold. **The default primary must never be the planner's own group**: it is the one most likely to be nearest the meet, so that default reproduces the unfair-6am case every time and the planner does not notice, being the one who rode three miles.
- **`src/subgroups/rendezvous.ts` CALLS NO ROUTER, and that is deliberate.** Ranking a few dozen candidates through the Routes API would be a Routes bill per keystroke on a proxied, per-request SKU—and the proposal is a suggestion the planner accepts, at which point the ordinary routing path draws the real road and every number is replaced by a measured one. Straight-line distance is the right precision for "is this a sane place to meet" and the wrong precision for "how long will it take"; the module never claims the second.
- **`src/members/policy.ts` HOLDS THE PERMISSION LADDER, AND `ride_perm`'S MEMBER ORDER IS NOT ITS RANK.** `view` < `comment` < `suggest` < `edit`, with `owner` above all four by construction rather than by being a rung—so an owner's `perm` column is never read, which is what lets demoting a co-owner be one column changing instead of two that can disagree. `PERM_RANK` is the only ordering and `atLeast()` is the only comparison; nothing may compare two enum members directly, for the same reason `visibility` cannot be sorted. **An invitation grants `suggest` and never `edit`**—`DEFAULT_PERM`, mirrored by the column default—and edit is always a deliberate promotion. **Edit means the builder and nothing more**: delete, visibility and the roster are `canAdminister`, which is role and not rank. A rider's rung is shown to the OWNER only (`canSeePerms`): the roster answers who is coming, and rendering rungs down it publishes a ranking of the riders to the riders.
- **CO-OWNERS, NOT OWNERSHIP TRANSFER, AND `rides.owner_id` STAYS SINGULAR.** Ziad's call, 2026-08-28. More than one member may hold `role = 'owner'`; `canRemove()`'s no-orphan rule narrowed from "an owner may not leave" to **"the LAST owner may not leave"**, and no owner may remove a DIFFERENT owner—co-owners hold equal power, so allowing it makes the ride belong to whoever presses the button first and the loser cannot undo it. `rides.owner_id` keeps meaning the creator and the QUOTA holder, because `rides.size_bytes` rolls up to `users.used_bytes` through one owner and `reconcileUsedBytes()` rebuilds every tally on that assumption. An `edit`-level rider's save therefore counts against the ride owner's quota, always.
- **`src/members/policy.ts` owns who may do what to a roster, and two of its rules say NO to somebody who outranks the person they are acting on.** An owner may not RSVP on a rider's behalf—the roster is read as "who said they are coming", and one forged row stops it meaning that—and an owner may not remove themselves, because a ride with no owner has nobody who can invite, resolve a vote or delete it. Both are easy to "fix" into a bug.
- **`src/votes/policy.ts` is the whole governance rule, and most of it is what happens on a tie: nothing.** A tie is the ORDINARY state rather than the edge one—a three-member ride with two alternates ties whenever one rider abstains—so `electWinner()` returning null is the common path, not the fallback. There is deliberately no quorum and no tie-break; see docs/decisions.md before adding either.
- **A vote points at a day by `uid`, never by `id`, and `days.uid` exists for exactly that.** `days.id` churns on every save and `alt_group` is renumbered densely, so neither can be stored. `alt_votes` cascades from `rides` and NOT from `days`, the same as `point_details`, which means the same obligation: `reconcileVotes()` in `src/votes/service.ts` deletes votes whose day left the payload, and `insertRideGraph` calls it. Skip that and a deleted alternate keeps counting forever.
- **`src/access/policy.ts` is the ONLY place the visibility table is written down, and `query.ts` is the only gate a route calls.** Before 2026-08-26 the same four-clause test lived in three hand-rolled copies—`getViewable` in `index.tsx` and one each in `handoff.tsx` and `roadbook.tsx`—and they agreed only because nobody had changed the rule. `canView(ride, viewer, grants)` is the boolean a route asks about one loaded ride; `LISTED_RIDE` is the constant predicate a list query filters on, derived from `isListed()` rather than restating it. **There is deliberately NO second `visibleToViewer(id)` implementation with EXISTS subqueries**: the only two list queries show LISTED rides and `friends` is not a listed level, so nothing needs one. If a viewer-dependent list is ever wanted, that form is the answer and it needs an agreement test against the boolean.
- **FOLLOWING GRANTS NO VISIBILITY, NOT AT ANY LEVEL, EVER.** Ziad's call, 2026-08-26. `follows` is a SECOND relation and deliberately not a mode of `friendships`: direction is the data, so there is no canonical ordering and no `status` column—a follow is done the moment it is made and undone by deleting the row. `canView()` does not know the table exists and must not learn. `followingRides()` in `src/access/query.ts` filters on `LISTED_RIDE`, so every row a feed shows is one `/explore` would show; if it ever selected `FRIEND_LISTED_RIDE`, `friends` visibility would be openable by anyone willing to press a button and the level would mean nothing. **A BLOCK TEARS DOWN BOTH FOLLOW ROWS**, via `dropFollowsBetween()` called from `blockRider()`—a surviving row leaves the blocked rider watching the blocker's feed, which is the thing a block exists to stop, and `canFollow()` refuses a block in EITHER direction for the same reason.
- **`/riders` AND `/friends` ARE ONE PAGE AT TWO URLS, and `src/routes/riders.tsx` is it.** Ziad's call, 2026-08-27 (#179): Friends and All riders as two tabs of one screen, with the friendship VERBS left behind in `routes/friends.tsx`—that file decides what may be DONE, this one decides what to SHOW. **This reversed a recorded decision** (Friends under the account menu, because the roster and a rider's own list are different questions) and the old reasoning is struck in `layout.tsx` and `docs/main-menu.md` rather than left to be re-discovered. `/friends` is kept rather than redirected because both friendship emails link to it; it opens the Friends tab. Both URLs set `navKey: 'riders'`, and the `friends` NavKey is gone under the rule already on that union—a key no NavItem carries is an `aria-current` that is wired and can never fire. **Most Active is deliberately absent** (#192): the page's lede promises names and handles only, and a leaderboard publishes every rider's activity to every other rider, which is a data-exposure decision rather than a UI one.
- **`originalIsCurrent()` in `src/maps/downloads.ts` is why an export is not the file you uploaded.** The download route prefers a stored original—rightly, because it carries styling, folders and per-point detail this app does not model—and **NOTHING REWRITES OR CLEARS THAT FILE WHEN THE BUILDER SAVES**. So the preference holds only while it is still true: `rides.original_stored_at` is stamped in the transaction that writes the file, and `updated_at` past it means the ride was rebuilt here. Same shape as `updated_at > thumb_built_at`, deliberately, rather than a second idea about how to ask "has this changed since". **NULL means current, never stale**—it means no original was ever stored, every caller checks `hasStored()` first, and the other reading would hand the lossy generated file to any row `drizzle/0023`'s backfill missed. Nothing is deleted: the file stays on disk, stays in the rider's quota, and the account archive still returns exactly what they uploaded.
- **`src/friends/policy.ts` owns the fact that a friendship row has no sides.** One row per pair under `rider_a < rider_b`, so `friendView(row, viewerId)` is the only thing that turns a row into the viewer's own terms and every rider-facing surface goes through it. Getting that backwards produces the two worst outcomes available here: a request that accepts itself, and a block the blocked rider can lift.
- **A friendship refusal is SILENT and IDENTICAL in every case.** No verb reports which rule stopped it, an unknown handle is indistinguishable from one that blocked you, and a blocked rider is still shown a working-looking Add friend button. That is not an oversight and it is not a greyed control waiting to be enabled—a distinguishable refusal is the notification a block must never be.
- **`test/fidelity.test.ts` is the per-format fidelity matrix, and it asserts the LOSSES as well as the wins.** One row per field per format, in two columns that deliberately disagree: `writes` is what a third-party tool opening the file sees, `reads` is what our own importer gets back. Per-day color is the worked example—KML and GeoJSON both write it and nothing reads it back, because a day's color is the viewer's business rather than the file's. **The native JSON is deliberately absent**: it carries everything, which is the whole point of it, and `test/native.test.ts` covers it against the same schema the builder's save uses. Note the trap the file itself walked into: `processKml` returns a `KmlResult` carrying `storedKml`, the entire sanitized document, so a naive `JSON.stringify(result)` finds every value the FILE holds and reports KML as carrying things nothing reads. `visible()` is what keeps the probes honest.
- **`test/viz-categories.test.ts` is the data-viz validator, and it compiles the SCSS to get its numbers.** The four categorical slots in `style/_dashboard.scss`, across all six palettes, in OKLab under normal vision and the three dichromacies, plus separation from the card and the track. `_dashboard.scss` claimed such a validator existed for weeks and the repo did not contain one. **It records a real failure rather than hiding it:** `$disabled` and `$interstate` collapse to ΔE 2.05 under tritanopia, which predates the fourth slot and is survivable only because the legend direct-labels every segment. Do not swap a slot by eye.
- `src/maps/alts.ts` is the single source of truth for what an alternate day means, mirrored by `public/js/alts.js` and pinned together by `test/alts.test.ts`. Both runtimes have to agree: the builder decides live which day is active and what the ride's mileage reads, and the server decides the same thing on save. A disagreement shows up as a builder displaying one total while the database stores another, with nothing raised.
- `src/maps/roles.ts` is the single source of truth for the 17 waypoint roles; the `waypoint_role` enum in `src/db/schema.ts`, the icons in `public/img/icons/`, and `ROLE_COLORS` in `src/maps/role-colors.ts` must all stay in sync with it. Four lists, held together by `test/roles.test.ts` and `test/role-colors.test.ts`.
- **`src/maps/role-colors.ts` is the seventeen-color categorical ring, and it deliberately does NOT follow the theme.** Seventeen categories cannot be made mutually distinguishable under dichromacy by any assignment, so shifting them with the colorblind palette would trade an honestly undifferentiable set for one that pretends otherwise. What makes the chart readable is that color is never the only cue there—every bar carries its own icon and its own text label. Generated by `utils/build-role-colors.mjs` and measured by its test; do not hand-edit a hue.
- **`test/palette-contrast.test.ts` is the contrast audit, and it compiles the SCSS to get its numbers.** All six palettes, every pair the app actually paints. It is the only thing standing between a nudged hue and an illegible theme—the values in `_palette.scss` were "reasoned rather than measured" for a week and were wrong in four places.
- `src/maps/filename.ts` is the source of truth for the export filename convention; `public/js/filename.js` mirrors it and `test/filename-client.test.ts` holds the two together. Same arrangement for `twist.ts`/`twist.js` and for `duration.ts`/`duration.js`—the last of those has a third copy to keep in step, `fmtDuration()` in `src/routes/roadbook.tsx`, which `test/duration.test.ts` also pins.

Anything that reads a table to decide whether to send lives outside it—`src/auth/notify.ts` and `src/feedback/notify.ts` are the two precedents.
- **A saved place is COPIED into a ride, never referenced.** Ziad's call, 2026-08-21. There is deliberately no `place_id` on `points`: a ride is a record of what the rider planned, so renaming or deleting a place must not reach back and rewrite a ride from last year—and points churn on every save anyway, so a foreign key would have to survive that for no gain. `placeToStop()` in `src/places/policy.ts` is that decision in code, mirrored client-side by `stopFromPlace()` in `public/js/builder.js`. **The consequence to state rather than treat as a bug: fixing a badly placed pin fixes future rides only.** A place carries the DURABLE half of stop details (phone, address, links) and never the per-trip half—inheriting last September's confirmation number would be worse than having none.
- **`place_groups` deletes with `set null`, not cascade.** Deleting a group keeps its places and makes them ungrouped; `groupPlaces()` renders them in their own section. A rider tidying up a folder name must not lose their saved locations, which is exactly what cascade would do.
- **`src/images/` is the ONLY upload path that touches a rider's image, and re-encoding is not optional.** `policy.ts` is pure: it sniffs the magic number and gates on size, and it is what refuses an SVG—a document that can carry script, which served from this origin is stored XSS. `process.ts` is the sharp half and always re-encodes to WebP, because bytes reaching a server are attacker-controlled whatever the page did to them. Parameterized by a target box so #99's avatars are a caller rather than a second implementation. `test/images.test.ts` pins all of it.
- **`src/maps/compress.ts` is the only place brotli is spoken, and `readMapFile()` in `storage.ts` is the only way to read a stored original.** Callers used to build a path and `readFile()` it, which was fine while one name was possible; there are two now (`19.gpx` and `19.gpx.br`), and two places to remember a fallback is one place to forget it. Both spellings are valid on disk—a half-migrated directory works—and nothing rewrites a file lazily on read.
- **`src/trash/` is the recycle bin, and `service.ts` holds the predicates that keep it invisible.** `LIVE_RIDE`, `LIVE_PLACE` and `LIVE_PLACE_GROUP` exist so an omission shows up in review as a missing import rather than as an absent `is null`. `policy.ts` is the pure half (the 30-day hold, `trashState()`, `canRestore()`); `purge.ts` is the only code in the app that destroys a ride. Rules mirrored from `src/account/policy.ts`, deliberately: the GTFO hold on `users` is the same mechanism one level up.
- **TWO RIDERS CAN PLAN ONE RIDE AT ONCE, AND WHAT PROTECTS THE WORK IS THE HASH, NOT THE CLAIM.** Ziad's call, 2026-08-30. The builder's `PUT` is still a whole-ride replace, but it is now guarded twice. `rides.rev` is checked under `for update` and a stale one is refused with a 409—that covers the RIDE-level fields, which have no finer unit: title, description, visibility, subgroups, anchors. Days are merged per uid against `days.content_hash`, so two riders on DIFFERENT days never collide at all. **`src/maps/day-merge.ts` is a THREE-WAY merge and the third leg is the one that looks redundant**: `dayBase` carries every uid the client held, because a day absent from the payload is either one the rider deleted or one somebody else added, and those need opposite answers—without it, one rider's save deletes every day the other has added. **`src/live/hub.ts` is presence and claims and it is a COURTESY**: in memory, gone on restart, gone on a dropped connection, and it must never be what stands between a rider and their work. A held day is marked, never disabled, for exactly that reason—a lock the server does not enforce must not be drawn as one.
- **`dayRevision()` IS NOT `dayFingerprint()`, AND MERGING THEM BREAKS ONE OF THEM.** `src/suggestions/policy.ts` deliberately ignores titles, colors and times so that renaming a day cannot invalidate a suggestion about its shape. A concurrent save asks the opposite question—did anybody touch this at all—and a rename is exactly what it must catch. One function cannot answer both. **The hash is computed in ONE place, on write, and `loadRidePayload` returns the column verbatim**: recomputing on read would require the write shape and the read shape to stay identical field for field forever, and the first divergence would make every day conflict with itself on every save, on rides nobody else had touched, with nothing to point at.
- **`src/maps/point-details.ts` is the private-stop-details boundary, and it is the only module that reads `point_details`.** Confirmation numbers, gate codes and phone numbers live in their own table rather than as columns on `points` for exactly one reason: `points` is what `ride.json` is built from and what every export serializes, so a private field stored there is one forgetful `select()` away from a public share. A separate table has to be JOINed to leak, and a join is visible in review. `canSeeDetails()` is the whole rule—**owner only, and deliberately blind to `visibility`**, because sharing a route is not sharing a reservation. Details reach exactly three surfaces: the builder's own load, `ride.json` for the owner, and the native JSON. They are stripped from GPX, KML, GeoJSON and CSV, and a clone drops them (`src/routes/builder.ts`)—a public ride is clonable by anyone.
- **`src/maps/manifest.ts` IS A DELIBERATE HOLE IN `planImport()`'s INVARIANT, and the invariant's own comment says so now.** filename.ts states that the drop box previews `planImport()` and the endpoint acts on it, "so the two cannot disagree about what a folder means". That held while the preview was read-only. The review table (#129) makes it editable, and a rider who can retype a date is a rider whose answer the server cannot re-derive—so the corrections travel with the upload and `planImport()` is demoted from the last word to the guess both sides start from. **No manifest means the old behavior exactly**, which is what keeps the form working with JavaScript off and keeps every API client unaffected.
- **THE IMPORT STAGES IN THE BROWSER, NOT ON THE SERVER.** Ziad's call, 2026-08-26. There is no stage id, no temp directory, no expiry sweep and no quota accounting for an import nobody finished: the page holds the files, the review edits a JS model, and Import posts the files and the manifest together in one multipart body. Two consequences to state rather than treat as bugs: **a zip cannot be reviewed**, because nothing unzips in the browser, so an archive's row says its days are read on upload; and **dropping a row means the file is never uploaded**, because the page rebuilds its own `<input type="file">` through a `DataTransfer` before submitting. That rebuild is verified rather than assumed—the manifest is built from what the input actually holds afterwards, so a browser that refuses the assignment degrades to "imports in the order shown" instead of failing the name check.
- **AN ORPHANED COMMENT DEMOTES TO THE RIDE; IT IS NEVER DELETED BY A SAVE. THAT IS THE OPPOSITE OF EVERY OTHER uid-KEYED CHILD OF A RIDE.** `point_details` and `alt_votes` are both reconciled AWAY when their uid leaves the payload, correctly, because they are data ABOUT a point. A comment is a thing a PERSON said, so `demoteOrphanComments()` in `src/comments/service.ts` clears `point_uid` and leaves the row—called from `insertRideGraph` beside the other two, and running for every saver because a demotion loses nothing. **`point_label` is denormalized at post time for exactly that moment**: the point is gone, there is nothing left to join to, and the label is the only thing keeping the comment from being about nothing. It is never updated afterwards. **Commenting is roster-only and never link-based**—a share link is permission to SEE a route, not to write on it, the same gate `/m/:slug/riders` and voting use.
- **`src/suggestions/policy.ts` IS THE HARD HALF OF #190, AND STALENESS IS DERIVED, NEVER STORED.** A suggestion is a WHOLE DAY proposed against that day as it was—not a field-level diff, because the builder deletes and re-inserts every point on every save and `uid` is the only identity that survives. `dayFingerprint()` hashes the point uids in order with their kind and their position rounded to about a meter: exactly what a suggestion is a proposal about, so a rename or a recolor does not invalidate one and a re-route's float noise does not either. A suggestion is stale when that fingerprint no longer matches, which means a day edited and then edited BACK correctly stops being stale—the case a stored flag gets wrong. **The fingerprint is taken server-side from the database, never from the client**, or a stale proposal could declare itself fresh, and it is re-checked on accept because the owner's list may be minutes old. **Accepting goes through `insertRideGraph` like any other save**, with one day swapped, rather than a second write path for "apply a day". **`canDecide` is the owner and deliberately NOT an `edit`-level rider**: accepting is deciding whose version of the ride is the ride.
- **`visibleTo()` in `src/feedback/policy.ts` is the private-bug feature.** There is no second mechanism: a report is invisible to everyone but its author and the owner until `state = 'published'`, and nothing publishes a bug by default. `state` (the owner's gate) and `status` (the rider-facing lifecycle) are two columns for exactly this reason.
- **TURNSTILE GUARDS THE FILE UPLOAD AND NOTHING ELSE.** Ziad's call, 2026-08-30, closing #132. `turnstileEnabled()` is ONE flag over the whole app—`TURNSTILE_SECRET_KEY.length > 0`—and it was wired to two endpoints. `POST /api/maps` works: `/import` renders the widget and the form posts `cf-turnstile-response`. `POST /api/rides` checked an `X-Turnstile-Token` header that **nothing sends**, so arming the upload gate would have 403'd "Plan a ride" for everybody. The gate is gone from the builder rather than fixed, because Turnstile asks "is this a human" and that route already asks harder—`requireActiveApi` is an account Ziad approved, `requireSameOrigin` is a request from the site, and a bot holding both is not stopped by a checkbox. The upload is different: it opens files strangers hand it and writes them to disk against a quota. **Do not re-add a token check to a builder route**; a token is single-use and expires in five minutes, so it cannot ride on an autosave that fires every three seconds, and rate limiting (#16) is the answer to that question.
- **One third-party script loads from a CDN, on the builder only:** SortableJS 1.15.7 from jsdelivr, for drag-to-reorder, pinned with an SRI hash and `crossorigin`. Approved 2026-08-15. It is not a mistake and not leftover—but note the builder degrades rather than breaks if it fails to load, and every row menu carries Move up / Move down as both the fallback and the keyboard path. Keep both properties if you touch it. Self-hosting the webfonts was a decision about **fonts**, not a general ban on CDNs.

## Conventions

- **Coordinates are `[lng, lat]`** everywhere in this app—storage, payloads, GeoJSON, exports.
- **A button is a highway guide sign by default.** Ziad's call, 2026-08-22: `.btn` carries the green field, the inset white keyline and an arrow at the right pointing east, with no extra class. `.btn-sign` still works and means the same thing—it is an alias kept because it reads as intent. `.arrow-left` puts the arrow back on the left pointing west, and the eight `.arrow-*` bearings override the direction. **Opting out is a named list, `$btn-flat` in `style/_chrome.scss`**, and a new variant gets the sign until it is added there. That is the intended failure: a button that inherits the house style by accident is better than one that quietly leaves it.
- **`REMOTE_ENV_KEYS` AND THE `printf` BLOCK IN `deploy.sh` ARE TWO LISTS ANSWERING TWO QUESTIONS, AND THE COMMENT SAID THEY WERE ONE UNTIL 2026-08-30.** The printf block is what gets SENT; `REMOTE_ENV_KEYS` is what the release REQUIRES. They had already diverged in the safe direction—`OWNER_EMAIL` and `PURGE_ACCOUNTS` are written and not required—and that is the correct shape rather than drift to be tidied away. **An optional key goes in the printf block alone, with a `:-` default**; adding it to `REMOTE_ENV_KEYS` makes its absence a hard failure, and the verifier greps `^KEY=.` so an EMPTY value does not satisfy it either. Since CI runs under `DEPLOY_SKIP_ENV` and stage deploys itself on every push to `main`, promoting a key before `push-env` has put the value on every server fails the next CI deploy after a full build. `TURNSTILE_*` is the worked example: sent, not required.
- **A build has a version and it comes from the commit, not the deploy.** `YYYY-MM-DD-HHMMPT`—the minute of HEAD's committer date in Pacific time, e.g. `2026-08-23-1834PT`. Ziad's call, 2026-08-23. Computed by `utils/deploy/deploy.sh`, shipped as `APP_VERSION`, and read by `src/version.ts`, which falls back to `dev`. Redeploying the same tree reports the same version because it is the same code. **The `PT` is part of the value, not a label**—a bare timestamp is read in the reader's own zone, and nothing parses this string, so do not add one that does. **A NEW KEY NEEDS TWO EDITS, AND MISSING THE SECOND IS SILENT**: the allow-list in `deploy.sh`, which decides what is written into the remote `.env`, AND a line in the `environment:` block of `docker-compose.prod.yml`, which is what actually reaches the process. Compose reads that `.env` for `${VAR}` substitution inside the compose file and nothing else, so a key on the allow-list that no compose line references is read by nobody. `APP_VERSION` and `BUILD_SHA` were on the allow-list and not in the block from 2026-08-23 to 2026-08-26, which is why **every deployed environment reported its version as `dev`** and every feedback report named no commit—the container starts and passes its healthcheck either way. `PURGE_ACCOUNTS` is in the same state and is deliberately being left there for now; wiring it up arms a destructive sweep and is Ziad's call.
- **Release notes are `src/content/release-notes.html`**, read through `views/content.ts` like the FAQ, and served twice: the page at `/release-notes` and the fragment at `/api/release-notes` that the modal fetches on first open. Add a release by copying the block at the top of the file. Every file in `src/content/` must also be registered in `test/content.test.ts`, which fails loudly when one is not.
- **Formatting is prettier**, configured in `.prettierrc`. Do not argue with it; note that `public/js/**` and SCSS have deliberate per-glob overrides.
- **Prose is never hard-wrapped.** One line per paragraph, soft-wrapped by the editor. Em dashes are tight (`word—word`); use a spaced en dash when a line wants air. The pre-commit hook fixes and re-stages.
- **Widows are a CSS problem first.** `text-wrap: pretty` is set on body copy in `style/_base.scss` and covers every page a browser renders, so page copy needs nothing hand-placed. Two surfaces are outside it and bind their own last two words with `&nbsp;`: `src/emails/`, because no mail client supports the property, and the printed roadbook. In static JSX write the entity straight into the markup—esbuild decodes it to U+00A0 while transpiling. For a string shared between an email's HTML and text arms, use `noWidow()` from `src/views/widow.ts`, so only the HTML arm carries the character; a text/plain part must not.
- **Views are Hono JSX** (`jsxImportSource: hono/jsx`, no React, no bundler). JSX escapes by default; `raw()` is the opt-out.
- **Tests are Vitest under `test/`**, named `*.test.ts`, pure logic only.
- **Schema changes ship as generated migrations** committed alongside the `schema.ts` change—SQL and `drizzle/meta/` both.
- **Branches** are `type/kebab-subject`; commits are Conventional Commits.

## Gotchas

Things an agent gets wrong by default. This section is why the file exists.

- **A document that disagrees with the code loses.** That has happened repeatedly here and has already caused a GitHub issue to be filed for finished work. Look at the files before believing any checklist.
- **`[lng, lat]` vs `{lat, lng}`.** Only `google.maps` speaks `{lat, lng}`, and exactly two places convert: `toLatLng`/`fromLatLng` in `public/js/map-common.js`, and `toGoogleWaypoint` in `src/routes/routing.ts`. A transposed pair still renders, just in the wrong hemisphere. GeoJSON agrees with us—do not "fix" it. Pinned by `test/round-trip.test.ts`.
- **Only active days count, and there is no single place that enforces it.** `rideTotals()` covers the stored caches, `loadRideForExport()` covers every lossy export and the roadbook and the hand-off page, five predicates in `src/stats/query.ts` cover the dashboard, and `ride-time.js` and the builder's own readout cover the two clients. A new surface that sums days has to opt in. `loadNativeRide()` and `loadRidePayload()` deliberately do the opposite and keep every day—they are the lossless paths.
- **THE BUILDER'S TIMELINE SPANS THE ACTIVE DAY, THE VIEWER'S SPANS THE RIDE, AND THE LIT DAY IS THE ONE BEING EDITED.** Ziad's call, 2026-08-30, closing #222 and #214 with one change. A slider stretched over a 72-hour ride spends most of its travel on the overnights and gives an hour of Saturday afternoon a few pixels—measured at 17.75x the resolution on a four-day ride once scoped. `state.timeScope` in `builder.js` is `"day"` (default) or `"ride"`, flipped by `#time-scope` in the bar; the viewer never renders that button, because reading a ride is not editing one and there is no active day there to scope to. Three things follow. **`applyFocus()` lights `focusedIndex()`, never the moment's day**—it used to light the moment's, which is the same answer right up until a rider scrubs and then clicks into a different day, and what they got was the day they were editing dimmed behind the one the slider was parked on. **The leg highlight is drawn only while the moment is ON the lit day**, or a bright leg is stranded across a day at `DIM_OPACITY`. **The readout captions the SLIDER, not the map**: in ride scope those are two questions with two right answers, and the line naming Day 1 while Day 3 is lit is correct. The consequence to state rather than treat as a bug: in day scope the bar hides on an undated day even when the ride has dates, and the scope button goes with it.
- **`activeNow()` IN THE BUILDER IS NOT `activeAtMoment()`, AND THAT IS WHAT MAKES OVERLAPPING DAYS RESOLVE.** In day scope the day is already known, so the moment is resolved against it with `activeAt(day, offset)` directly. `activeAtMoment()` walks the list and returns the FIRST day whose span contains the moment, which is right when it is searching and wrong when the answer is already held: it skips losing alternates, so a rider editing one gets back another day's index, and four days sharing a start date—which real rides have—all resolve to the first of them. Verified live on ride 15: ride scope answers "Day 3", day scope answers "Day 5", and Day 5 is the one on screen. `daySpan()` is the other half and deliberately disagrees with `rideSpan()` about a losing alternate: the ride's length must not include a day the rider decided against, but a rider who clicked into that alternate to work on it is looking at exactly that day.
- **`ride-time.js` skips losing alternates INSIDE the module, never by filtering the array at a call site.** `activeAtMoment()` returns `dayIndex`, which both clients feed straight back into `state.days[i]` and `setLegHighlight(map, i, …)`. Hand it a filtered array and every index past the first ghost is off by one, silently, and the map highlights the wrong road. **The same trap one level down is why it returns `pointIndex` and not the old `stopIndex`/`poiIndex` pair**: those indexed their own filtered arrays, so a caller holding the ordered list had to filter it the same way to read the answer.
- **`daySchedule()` is a plain walk and must stay one.** Dwell at `points[i]`, ride `legs[i]`, dwell at `points[i+1]`. It used to project every POI onto the day's concatenated track, sort by that distance, and cut the leg a POI landed inside at the right fraction—with the distances passed in by the caller as `poiDistsM`, because a builder POI has no stored `distFromStartMi` until it is saved. All of that existed only because a POI anchored no leg. Do not bring any of it back.
- **THE MERGED DAY SET MUST BE COMPLETE BEFORE `insertRideGraph()` IS CALLED.** That function reconciles votes, comments and point details against the uid set of the payload it is given—`reconcileVotes`, `demoteOrphanComments` and `writePointDetails` all do. Hand it one rider's partial day list and it deletes the OTHER rider's votes and orphans their comments, silently, with nothing raised anywhere. The merge in the PUT therefore assembles the whole set first and only then writes.
- **A CLIENT MUST REBASE ONLY THE DAYS IT ACTUALLY HOLDS.** The PUT returns every stored day's new hash, and rebasing that map wholesale is the trap: it includes days another rider has just added, this builder has never seen them, and **a uid in `dayBase` that is missing from the payload is precisely how the merge is told the rider deleted it.** The next autosave would erase their work three seconds later. `builder.js` filters the response against `state.days` for that reason.
- **A LIVE REFRESH RE-RENDERS THE DAY LIST, WHICH IS #188 ARRIVING BY ANOTHER ROUTE.** Rebuilding the list under a rider destroys the input they are typing in and drops focus to `<body>`. `state.dirty` does NOT cover it—`change` fires on blur, so a rider mid-word is still clean—so the refresh also checks whether the caret is inside `#day-list` and takes nothing if it is. **And the day's index is re-read AFTER the fetch**, because an `await` happened and splicing at a stale index replaces the wrong day.
- **`points.uid` is the point's identity; `points.id` is not.** The builder's `PUT` deletes and re-inserts every day and point on every save, so ids churn constantly—that was accepted deliberately on 2026-08-15 and has not changed. Anything that must reference a point across a save uses `uid`, which the CLIENT mints (`uid()` in `public/js/builder.js`, mirroring `newUid()` in `src/maps/uid.ts`—same alphabet and length, or the save 400s). **There are two places points are inserted and both must supply a uid:** `insertRideGraph` and the lossy import in `src/routes/maps.ts`. A missing one fails the NOT NULL at runtime with nothing useful to say.
- **A NON-OWNER'S SAVE MUST NOT RECONCILE `point_details`, AND GETTING THAT WRONG DESTROYS DATA SILENTLY.** An `edit`-level member loads the ride through `detailsForViewer()`, which hands a non-owner an EMPTY map—correctly, because a confirmation number is not shared by sharing a route. Their save then posts a payload with no details in it, and a reconciling write reads that as "the rider cleared every one of them" and deletes the lot: every gate code and reservation on the ride, gone, because somebody they trusted to move a stop moved one. `insertRideGraph`'s `DetailsMode` is the guard—`preserve` for a non-owner, which writes and deletes nothing. The cost is that details belonging to a point the editor DELETED linger as orphans until the owner's next save reconciles them, which is the right way round: an orphan is recoverable and a deletion is not.
- **`point_details` cascades from `rides`, not from `days`.** That is what makes a stop's confirmation number survive the `delete(days)` at the top of every save. The flip side: nothing else cleans it up, so `writePointDetails` in `ride-graph.ts` deletes rows whose uid left the payload. Skip that and a deleted stop's gate code lives forever.
- **Autocomplete and Text Search answer different questions, and only one of them can answer a category.** Autocomplete matches NAMES and ADDRESSES: asked for "gas station in oakdale ca" it returns the businesses literally called that, which in Oakdale is one, while the ARCO and the Shell go unmentioned. Enumerating a KIND of place is Text Search, a different endpoint on a pricier SKU, proxied at `/api/places/search` and cached for that reason. `place-query.js` decides which question was asked and is deliberately conservative—"Shell" and "Chevron" are names, not categories, so they never spend a Text Search call. **Text Search reads "X in Y" itself**, so the place is never geocoded separately; `near` is only for a category chip, which has no place in its text.
- **The two Google keys need different API lists, and the failure is a 403 that looks like an outage.** `GMAPS_SERVER_KEY` must carry Places API (New) or every Text Search comes back `403 API_KEY_SERVICE_BLOCKED`—a console change, not a code problem, which is why the route detects that exact reason and returns a 503 naming it. The browser key already has Places because the Autocomplete uses it, so having one working search and one broken one is the expected symptom of forgetting.
- **A CATEGORY IS A REASON TO STOP: picking one promotes a point, clearing the last one demotes it.** Ziad's call, 2026-08-24. Tagging a point Gas already says you mean to be there, so requiring "make this a stop" afterwards was two actions for one intention. Three consequences: **a point created with roles arrives as a stop**, which is every category-chip result, every category query and every saved place filed under one; **demoting clears the roles**, or a POI would sit there tagged Gas and anything re-deriving one from the other would promote it straight back; and **untagging the day's only stop is refused**, because the day would have none and `payload()` drops such a day whole. The row menu keeps both items for what a category cannot say—a stop with no reason given, which imports and the first-point rule both produce.
- **It is an INTERACTION rule, not a schema one.** `points.kind` stays its own column and an untagged stop is a real, valid shape; nothing derives `kind` from `roles` on the server. Do not "simplify" it into a computed field—the importer writes untagged stops and so does the auto-promoted first point of every day.
- **THE SEARCH SCOPE IS TWO NAMED SEGMENTS AND ITS WIDTH IS A CONSTANT. A SLIDER IS THE THING THAT WAS REJECTED.** Ziad's call, 2026-08-31, hours after #50 shipped as a checkbox labeled "Along the day" beside a 1–50 mile range input. Three faults, and the third is the one that generalizes. **A checkbox never says what unchecking it does**, so the rider is left to infer the other half; `Near here | Along the day` states both. **`CORRIDOR_MI` is 15 and there is no control for it**, because the width a detour is worth is a preference and not a per-search decision—asking for it every time put two controls in front of a question the rider had already answered by tapping a chip; if it ever needs to move it belongs in ride preferences, once. And **the control renders ONCE PER DAY, on the day's own bottom add-row and never on an insert slot**: `state.corridorOn` is one session-wide flag, so a copy in every add-row meant a six-point day drawing seven of them and a `querySelectorAll` hand-syncing the lot on every change—one control cannot disagree with itself. The click handler patches every `.scope-btn` and every chip tooltip in place and **must never call `renderDayList()`**, which would destroy whatever is in the add-row's field and drop focus to `<body>`—#188 reached from a control that has nothing to do with the day's contents.

- **THE FUEL RING'S EDGE PASSES THROUGH THE POINT THE RIDER RUNS DRY, AND THIS SHAPE WAS TRIED, REJECTED, AND ARRIVED AT AGAIN.** Ziad's call, 2026-08-31. The dry point is found on the ROAD—the last fill's mileage plus the binding bike's range, walked along the day's own polyline by `pointAtDistance()`—and the radius is the straight line from the rider to it. So the ring is not a range number drawn as a circle, which overclaims on any road that bends; its edge is a PLACE, and it collapses to nothing exactly as the rider arrives there. **The difference between the two attempts is the whole lesson and it is not the radius rule**: the first version made the ring chase a MOVING target, jumping to the next fuel stop whenever one came first and GROWING once the rider passed the dry point, so nothing about it could be read. The target is now only ever the dry point, it never moves while the rider approaches, and past it there is no ring. Same formula, and it behaves because the thing it points at holds still. **A middle version where the radius WAS the remaining fuel is also recorded as rejected**: it satisfied "range minus miles ridden" literally and drew a circle a rider cannot reach the edge of. The range is the SHORTEST tank in the group—what `groupRange()` answers, and what #52 was for. **THE RING'S TARGET AND THE WALL'S ARE TWO DIFFERENT QUESTIONS, WHICH IS WHY THERE ARE TWO FUNCTIONS.** `fuelReachM()` is how far the tank gets the rider, CAPPED at the end of the day; `dryDistanceM()` is where they run out, and null when they do not run out at all. Drawing the ring from the second was a real defect, reported from a test ride with the pump set a few miles past empty: **past a rider's LAST refuel the tank outlasts the day, so there was no dry point, so there was no ring**—for the rest of the day, with the refuel detected perfectly the whole time. A ring reaching the end of the day is a true statement (that is as far as this fuel has to get them) and the wall is what says whether they make it, so **a ring with no wall inside it means the day is covered**.
- **THE DRY MARKER OUTLIVES THE RING, and that is not an inconsistency.** `dryDistanceM()` keeps returning the point once the rider is past it, because it is a fact about the DAY rather than about where they are—dropping it made the map go quiet at exactly the moment the plan was worst. The RING goes at the same moment, because a ring drawn back to a point behind you grows as you carry on, which is the defect that sank the first version. So past empty: marker yes, ring no. **The marker is a short red bar laid ACROSS the road, like a wall**—Ziad's call, 2026-08-31, replacing a hollow ring, because a dot on a line reads as another stop and this is the opposite of a stop. `bearingAtDistance()` in `route-shape.js` gives the road's heading there and `setMomentOverlay()` rotates the bar by exactly that: the bar is authored horizontal, which is screen bearing 90, and `rotate()` turns clockwise from there, so the angle is the bearing itself and **not the bearing plus ninety**. It is fixed PIXELS rather than meters—a polyline in real distance is invisible at low zoom and a mile wide at high zoom, and a wall is a symbol. The rotation goes on an inner `<i>` because `AdvancedMarkerElement` manages the transform of the content root it is handed and overwrites one set there. The ring stays `$brand`, because a distance is not a verdict.
- **`$signal` IS THE BLUE GO LIGHT IN THIS PALETTE. THE RED IS `$stop`.** Both names read as "the urgent one" and only one is: `--signal` is `#3a76f0`, deliberately pulled toward blue because it is a signal HEAD, and `--stop` is `#cc0000`. The dry marker shipped blue for one build on exactly this confusion. `$warning` is a third thing again—the amber of a warning diamond, which is what `.row-dist-dry` uses to say "put a fuel stop in". Advice is amber, a wall is red, and go is blue.
- **THE MOMENT DOT IS DRAWN ON WHATEVER DAY THE MOMENT FALLS ON; THE LEG HIGHLIGHT IS NOT.** They look like the same rule and are not. A highlight is a stretch of the day's own line, so drawn bright across a day dimmed to `DIM_OPACITY` it reads as neither state—which is why `applyFocus()` gates it on the lit day and the viewer's `paintFocus()` drops it on a hover. A dot is a discrete overlay above every route and has no such ambiguity, so gating it the same way would make ride scope—whose entire purpose is scrubbing the whole ride—show nothing for most of its travel. A HOVER still suppresses both in the viewer: hovering a legend row asks which day this is, which is not a question about where anybody would be at any moment.
- **`activeAt()` RETURNS `legFraction` AND IT IS A FRACTION OF TIME, NOT OF DISTANCE.** Time is the axis the scrubber moves along, so a dot placed by it keeps step with the clock printed beside it; placing it by distance would have the dot lag or race on any leg whose speed is not constant, which is every real one. It is an added field rather than a new function so a caller that only wants the leg reads the shape it always read—but note `toEqual` on the whole object is how the existing tests were written, so an added field breaks them loudly rather than silently, which is the right way round.
- **THE VIEWER IS SENT `miles` AND `fuelType` AND NOTHING ELSE OF `GroupRange`, AND ONLY TO A MEMBER.** `riderName` and `bikeLabel` are roster facts, and a roster is gated on MEMBERSHIP rather than on visibility—so a stranger holding a public ride's link must not learn who is coming or what they ride. They are dropped at the call site in `src/index.tsx` rather than downstream, because the range circle needs a number and a fuel type and the two identifying fields have no use on that surface at all. **Null for a non-member is indistinguishable from null for a member with no bike on file**, deliberately: the absence of a circle must not report whether somebody is on the roster.
- **`setMomentOverlay()` IS NOT `setMoment()`.** `builder.js` already owns the second name for the timeline's own setter, and a plain destructure of the map API collides with it—which fails as `Uncaught SyntaxError: Identifier 'setMoment' has already been declared` and takes the whole builder with it, timeline included. They are also two different things: one sets WHEN, the other draws WHERE that lands.

- **The category picker's open state lives in `state.rolesOpen`, not in the DOM.** Picking a category changes the kind, which renumbers every stop below it, so the row has to be re-rendered—and a picker whose openness was only a `hidden` attribute slammed shut after every tap. Same reasoning as `state.insertAt` for the insert-between rows; both are cleared by `renderDays()` because a delete or a reorder shifts the indices they are expressed in.
- **`poi` is BOTH a role and a kind, and they mean nearly opposite things.** The kind is somewhere you ride past; the role is somewhere you stop to look at something. The role is labeled **Sight** on every rider-facing surface for exactly this reason and keeps the identifier `poi` in code, the `waypoint_role` enum and `ROLE_META`—renaming the enum value is a migration over every stored point. Do not "fix" the label back.
- **The date format members are real locale tags, and that is what makes the CLOCK follow.** `src/views/date-format.ts` stores `en-US` / `en-GB` / `en-CA` rather than an abstract `mdy`/`dmy`/`ymd`, so Intl decides the digit order, the 12-vs-24-hour clock and the padding together—a British rider gets `24/08/2026` AND `16:00`. `fmtClock` uses `timeStyle: 'short'` for the same reason: spelling out `hour`/`minute` imposed our padding on every locale. Adding a locale is one enum member and no formatter changes.
- **Number grouping is still hardcoded `en-US` in `src/stats/shape.ts`, on purpose.** All three date-format members are English and group identically as `1,234`, so threading a format through ten `fmtMiles`/`fmtCount` call sites would change nothing anyone can see. `fmtNumber` in date-format.ts exists for the day a member like `de-DE` (`1.234`) lands.
- **`user_profiles` rows are created LAZILY, by the settings upsert.** So most riders have no row, which is what lets `dateFormatFor` fall through to `Accept-Language` and give a German browser day-first without anyone choosing. The consequence: an upsert that creates a row to save some OTHER preference must seed `date_format` from the header on INSERT and leave it out of the update set, or saving a duration preference silently stamps `en-US` over what the header was already giving them. All three handlers in `settings.tsx` do this; a fourth one has to as well. **Note that this exact warning was already written when the appearance handler was added and the handler skipped it anyway**—it shipped seeding neither, so from the day themes landed until 2026-08-27 a rider whose dates came from `Accept-Language` had them silently stamped to `en-US` the first time they touched the palette. The rule is easy to read and easy to not apply.
- **`null` is not zero.** Twistiness `null` means nothing measured it; `0` means the road is straight. Same for `dist_from_start_m` on a trackless import. A format that guesses is indistinguishable from one that knows.
- **`dist_from_start_m` is the prefix sum of the legs before a point, for BOTH kinds.** There used to be two algorithms split by kind—a prefix for stops, a nearest-vertex projection onto the concatenated track for POIs, because a POI had no leg boundary of its own. Every point has one now, so the prefix is the answer for all of them: exact rather than approximate, and never null on a day that has legs. `distFromStartAlongTrack()` survives for the lossy import path only, where a GPX waypoint arrives with no position and the track is the only thing that can place it.
- **`rides.size_bytes` must name every byte column.** The app increments `users.used_bytes` on import and the database decrements it from `size_bytes` on delete, so a column missing from that generated expression leaks quota on every delete, silently. **No longer permanently, as of 2026-08-24:** `src/account/quota-sweep.ts` rewrites every rider's tally from `sum(rides.size_bytes)` every five minutes, so a drift now has a five-minute life rather than an unbounded one. That is a safety net and not a licence—the sweep repairs the tally FROM the generated expression, so a byte column missing from it is still invisible to both.
- **A BIKE'S RANGE IS STORED IN METERS AND TYPED IN MILES, and `src/bikes/policy.ts` is the only place they meet.** `METERS_PER_MILE` is that boundary; above it everything is miles because that is what the form asks for, below it everything is meters because #150 will switch the site to metric and a value stored in whatever unit someone typed drifts on every round trip. A mile reaching the meters column reads as a bike that can go 290 where the rider said 180.
- **A form must never advertise a maximum the database rejects.** `MAX_RANGE_MILES` floors rather than using `metersToMiles`, which rounds: 2,000,000 m rounds UP to 1,243 mi, and 1,243 mi converts back past `ck_bike_range`. The rider would have got a 500 for entering exactly the number they were told was allowed.
- **`sharp` sets orientation with `withMetadata({orientation})`, NOT `withExif({IFD0:{Orientation}})`.** The second spelling writes a tag sharp reads back as 1, so a test fixture built that way is not sideways and the test passes for the wrong reason. `.rotate()` must also come FIRST in the pipeline: sharp writes no metadata to its output, so rotating later would drop the tag while leaving the pixels on their side.
- **A bike photo is `bike-<id>.webp` in the owner directory, and it deliberately does NOT parse as a stored ride original.** `parseStoredName()` needs a leading digit, so `listOwnerFiles()`, the account archive and `deleteMapFiles()` all skip it while `deleteOwnerDir()` still takes it on account purge. `photo_bytes` is counted on `bikes` and NOWHERE else—never in `users.used_bytes`, exactly as `feedback_attachments` does it.
- **`.br` HAS TO BE IN THE FILENAME BECAUSE BROTLI HAS NO MAGIC BYTES.** Gzip starts `1f 8b` and could be sniffed out of a file still called `19.gpx`; brotli cannot be identified from its bytes at all. That is why the suffix is load-bearing rather than cosmetic, and why `parseStoredName` captures it and `StoredFile` carries `compressed`. `.br` must never join `STORED_EXTS`—that list is the closed set of RIDER-supplied extensions the containment check leans on, and the suffix is ours.
- **`rides.size_bytes` NO LONGER DESCRIBES BYTES ON DISK.** The byte columns keep meaning the size of the original as the rider uploaded it, because an allowance must not depend on how well someone's file happened to zip. Disk holds roughly a fourteenth of that. "How much disk are we using" is a `du`, not a query, and there is deliberately no second column—`size_bytes` means one thing.
- **The account archive must DECOMPRESS on the way in, and this is the sharp edge of the whole compression change.** Its zip entries are named `.gpx`; putting brotli bytes under that name hands a rider a backup that silently will not open, and nothing anywhere would raise it. `src/account/export.ts` goes through `readMapFile()` for exactly this reason.
- **`ALTER COLUMN ... SET DEFAULT` reaches new rows only, so a changed default needs a hand-written `UPDATE` beside it.** `drizzle/0012` is the worked example: the differ emitted the `SET DEFAULT` for the 100 MB quota and nothing else, which would have raised the allowance for riders who do not exist yet and left every current one at 25 MB. Scope the UPDATE to rows still holding the OLD default, or a quota somebody set by hand is silently discarded.
- **THE `deleted_at is null` IN `reconcileUsedBytes()` IS LOAD-BEARING.** Trashing a ride frees its quota on the spot while the row and its files stay for thirty days. Drop that predicate and the five-minute quota sweep adds the bytes straight back—the rider watches their meter fall and then silently rise, and every trash is undone as far as the allowance is concerned. Nothing raises anything.
- **`uq_place_group_name` is PARTIAL, which breaks a bare `ON CONFLICT`.** Binning a group frees its name immediately (`where deleted_at is null`), and Postgres cannot infer a partial unique index from a column list alone—`createGroup()` must restate the predicate via drizzle's `where` option or the insert fails outright with "no unique or exclusion constraint matching". There is no type error and no test: places have no database-backed tests, so it surfaces as a 500 on "create a group".
- **A purge removes FILES FIRST and the row SECOND**, which is the opposite of what the old hard delete did and is not a mistake. Row-first leaves orphaned files if the process dies between the two, because the row that named them is gone. Files-first leaves a claimed row whose files are already removed, and the stale-claim reclaim (`CLAIM_STALE_MS`) finishes it. `deleteMapFiles` is idempotent, so the retry costs nothing.
- **A claim column has to expire or it strands the row it was protecting.** `purge_started_at` stops two sweeps purging the same row at once; without the stale reclaim, a process that dies mid-purge leaves that row claimed forever, never re-selected and half-destroyed.
- **The account purge had no runner at all until 2026-08-26.** `/account/delete` stamped `purge_after`, locked the rider out and showed them a destruction date, and nothing destroyed anything—`src/account/purge.ts` did not exist although `policy.ts` referred to it. It is now gated behind `PURGE_ACCOUNTS` precisely because its first pass will find everyone who has been overdue for however long that was.
- **THE `visibility` ENUM'S MEMBER ORDER IS NOT ITS OPENNESS.** `friends` is last because `ALTER TYPE ... ADD VALUE` appends and a pgEnum's order is fixed once created; putting it "in the right place" means rebuilding every column using the type. Nothing may sort by it, compare with it, or read it and decide what a member means—`canView()` is the rule and `isListed()` is the list question.
- **A LIST OF THE OPEN LEVELS GOES STALE; THE EXCLUSION DOES NOT.** `offerPublicStart()` in `builder.js` asked `visibility === 'public' || === 'unlisted'` and would silently have stopped firing for `friends`—which is a pin on the rider's house shown to everyone they ride with. It reads `!== 'private'` now. Same shape as the four `count(*) filter` clauses in `src/stats/query.ts`: a level missing from that list is a ride missing from the dashboard chart, whose total is the sum of those counts and is checked against nothing.
- **`ride_subgroups` IS THE ONE CHILD OF A RIDE THAT IS NOT CHURNED ON SAVE.** Days, points and legs are all deleted and re-inserted by the builder's `PUT`; these are reconciled by uid instead, because `ride_members.subgroup_id` and `rides.primary_subgroup_id` point at them and a delete-and-reinsert would null every one on the first edit. `reconcileSubgroups()` runs BEFORE the days, because `days.subgroup_id` is resolved through the map it returns.
- **DWELL AND SLACK SUM IN A PLANNED SCHEDULE, and only differ under the `meet` anchor.** Stated because the obvious claim is wrong and was written into the first draft of `schedule.ts`: moving a minute from one to the other changes no time the solver returns under `departure` or `arrival`. What actually differs is robustness under delay—which a static plan cannot show—and what the roadbook tells a rider. Do not "simplify" them into one column on the strength of the arithmetic.
- **A DIVERT-MINIMISING RENDEZVOUS PROPOSER CHEATS**, and a failing test is what caught it: a group far off the trunk gets its smallest divert by meeting a few miles short of the destination, where the two groups ride together for twenty minutes and the exercise was pointless. `minSharedFraction` is the floor that stops it. Any change to the scoring has to keep it.
- **YOU CAN ONLY ADD A FRIEND TO A RIDE.** There is no token, no email and no invite link, and that is not an unfinished feature—it is what let membership ship at all, because a friend already has an active account and already passed approval. See docs/decisions.md. The consequence to state rather than treat as a bug: **you cannot put somebody on a ride until you are friends**, which is one extra step for a rider who only wants to share a route, and unlisted and public links are the right tool for that.
- **THE OWNER IS A MEMBER OF THEIR OWN RIDE, and `seedOwner()` runs in the same transaction as every ride insert.** All four creating paths call it and `drizzle/0015` backfilled every existing ride. A fifth path that forgets produces a ride with an empty roster whose owner is standing right there, and every reader that then has to ask about `rides.owner_id` separately is a reader that can forget to.
- **A ROSTER IS GATED ON MEMBERSHIP, NOT VISIBILITY.** A public ride is readable by anyone and `/m/:slug/riders` is not. Who is coming on a ride is a fact about people; a share link is permission to see a route. Voting has the same gate for a sharper reason: a public ride would otherwise let anyone on the internet pick which road it takes.
- **`/riders` MUST FILTER BOTH HALVES OF A BLOCKED PAIR**, via `notBlockedWith()` in `src/friends/service.ts`. Without it the roster is a way around a block and its search box is a way around it by name. Symmetric on purpose: the blocker does not want to see them, and the blocked rider must not be shown who blocked them.
- **A LIST REGION THAT RE-RENDERS ITSELF ON A FIELD SAVE EATS THE RIDER'S NEXT CLICK.** `change` fires on BLUR, so the click carrying a rider from one field to the next is what triggers the save—and rebuilding `host.innerHTML` when the response lands destroys the field they have already focused, dropping focus to `<body>`. Every field after the first edit then needs clicking twice, and the second click works only because there is nothing left to save. That was #188 in `paddock.js` and the same defect in `places.js`, which it was deliberately mirrored from. **The rule: only a change that genuinely MOVES a row earns a re-render.** Bikes sort by `position`, so no field on that form can reorder anything and the row is patched in place. Places sort by NAME and still are not re-rendered on a rename—a list re-sorting under a cursor mid-typing is its own defect, and the row reaches its new place on the next load. Only a group CHANGE re-renders, because the row leaves one section for another and focus is on a `<select>` the rider has just committed to.
- **The `hours` duration format carries TWO decimals, and one is not a smaller version of the same thing.** At one place the format can only express six-minute boundaries, so the builder's blur handler silently REWROTE every value off that grid: a 15-minute stop came back `0.3` and read as 18 the next time anything parsed it, growing each time the rider touched the row. Two round-trips all 43,201 storable minutes, which `test/duration.test.ts` asserts exhaustively rather than by sampling—the old test allowed a three-minute loss and the corruption fitted inside it. Also note every numeric group in the parser is built from one `NUM` source that accepts a LEADING decimal point: `.25` matched nothing before #189 and the field simply emptied itself, on the one input a rider reaches for when they want a short stop.
- **`--timeline-height` IS A RESERVE AND IT WAS THREE PIXELS SHORT FOR TWO WEEKS.** Nothing measures the bar—the phone sheet's stacking and the feedback dock both clear it from a declared number—so a bar that outgrows the declaration under-clears by the difference, silently, with no symptom but a shrinking gap. It read `3.4em` against a root font size of 14px, so 47.6px against a builder bar measured at 51px. It is `4em` now—56px—and both bars measure 55px, which is one pixel of headroom. **Measure in the BUILDER**: it carries the scope button and the viewer does not, so the viewer can pass a number the builder overruns. Both grew to 55px when #229's fuel toggle landed in `.time-head`; the viewer's was 46px before it, which is how little slack a third control there would have.
- **A NEW CLIENT HELPER NEEDS TWO EDITS AND MISSING THE SECOND IS SILENT.** The module in `public/js/`, AND a `<script>` line in the `scripts:` block of `src/routes/builder.ts`. Without the tag the global is `undefined`, and what happens next depends only on where it is read: `day-split.js` was read during the row render, so the whole day list came out EMPTY on a ride with five points—the #224 shape—while `corridor.js` is read only inside a click handler, so the page looked perfect and would have thrown the first time a rider used the feature. Both were missed on the same afternoon, 2026-08-31, which is why this is written down: the module and its tag are in two files and nothing checks that a `window.TB*` a page reads is a `window.TB*` the page loads. Same shape as the deploy allow-list needing a matching compose line.
- **`.tb-marker` is deliberately `0×0`** in `style/_map.scss`. An `AdvancedMarkerElement` anchors its content at bottom-center, so a zero-size wrapper puts the anchor on the point and the negative-margin offsets keep working. Give it a size and every marker drifts.
- **A TYPED DAY NAME OUTRANKS THE FILE'S OWN, AND AN UNTOUCHED BOX DOES NOT.** The review table shows only what the FILENAME said, because nothing in the browser opens a GPX to read its `<trk><name>`. So an empty name field is "I did not answer" and the file's internal name still wins, while a name the rider typed beats everything. **The box is PRE-FILLED, so `import.js` tracks whether each name is still its own guess (`titleAuto`, the same flag the ride name uses) and posts a title only where the rider edited one.** Without that every row posts as though it were typed, and the same file imports under two different day names depending on whether JavaScript ran—measured on a GPX whose track is named `Oakland to Mt Shasta`, which came back as `Oakland To Mt Shasta`, capitalized by `titleFromSlug` out of the filename. The DATE is the opposite and for the same reason: it IS shown in full, so clearing it means undated and the review's null wins. Both rules live in `addDays` in `src/routes/maps.ts`; getting either backwards makes a correction silently do nothing, which is the whole complaint #129 was filed about.
- **`GET /api/rides/:id` SWALLOWS ANY `/api/rides/<word>` YOU ADD LATER.** The export search was `/api/rides/search` for about ten minutes and answered `{"error":"not found"}`—a lookup for a ride whose id is the word "search", from a module mounted earlier in `index.tsx`. It is `/api/export/search` now. Reordering the mounts fixes it and breaks again the next time a line moves; a path that cannot collide is the fix that stays fixed.
- **A SEARCH BOX'S DATE MEANS THE DAYS' DATES, NEVER `rides.created_at`.** A ride planned in March for a trip in August is the normal case, so the two are routinely months apart and the second answer is never the one a rider wanted. `src/maps/ride-search.ts` is the pure half; the EXISTS subquery in `routes/import.tsx` is the other. A bare month name is the one query that ORs its two readings rather than ANDing them—"august" means both rides ridden in August and a ride called August Loop, and picking one silently hides the other.
- **A day is drawn as one polyline**, the concatenated geometry of all its legs, with the duplicate vertex dropped at each joint and no indices consumed by an empty leg. Turning a drag index back into a leg plus a via-point slot is the entire job of `public/js/route-shape.js`. Do not switch to one polyline per leg—the layer-id contract every caller depends on assumes otherwise.
- **Two points in the same place get a zero-length `[v, v]` leg, not a one-coordinate one.** `legSchema.geometry` requires two, and duplicating a point deliberately puts the copy on top of its original. This is also how `splitDayTrack` handles a track with fewer vertices than points, which is what replaced the old demote-the-overflow-to-POIs mechanism—demotion freed a vertex only while a POI consumed none.
- **THE PROXY OWNS THE HOST PORTS AND THE COLORS PUBLISH NOTHING.** `proxy/upstream.caddy` on the NAS is ONE LINE and is the single source of truth for which color is serving—it is literally what Caddy is reading, so there is no second answer to drift from. `live_color()` in `utils/deploy/lib.sh` is the only implementation; `docker ps` is deliberately NOT used, because during a cutover both colors run and the whole point of the design is that "running" and "serving" are different states. **That file is gitignored and must stay that way.** It is also bind-mounted as a FILE: if it does not exist on the host when the proxy starts, Docker creates a DIRECTORY at that path and Caddy fails to read its own config with an error that mentions nothing about mounts—which is why `deploy.sh` seeds it before ever bringing the proxy up.
- **THE IMAGE IS PUSHED TO A REGISTRY AND PULLED BY THE NAS; IT IS NOT PIPED OVER SSH.** Changed 2026-08-29. It used to be `docker build` locally, `docker save | gzip`, and a few hundred MB streamed down the SSH connection—fine over a LAN, a poor fit for the Cloudflare Tunnel the NAS sits behind. **The tag is the commit, and that is a correctness property**: `routeloop:latest` and `routeloop:stage` were mutable, so the health gate's assertion that `/healthz` reports the expected SHA was the only thing between a Compose that decided the service was up-to-date and a deploy that silently changed nothing. An immutable per-commit tag makes that unreachable, and makes a rollback to any earlier build a tag change plus a recreate rather than a checkout and a rebuild. **A dirty tree gets `<sha>-dirty-<timestamp>`** so `--force` can still ship uncommitted work without publishing it under a name that claims to be that commit. Both registry logins are optional and skipped when no token is set, so the GHCR package's visibility is a decision made in GitHub's UI rather than in code.
- **A GHCR PACKAGE PUSHED FROM A LAPTOP IS USER-SCOPED AND UNLINKED, AND A WORKFLOW CANNOT WRITE TO IT.** `ghcr.io/feralcreative/routeloop` was created by a personal token, so it belongs to the USER rather than to the repository—and a workflow's `GITHUB_TOKEN` only ever gets write access to packages the repository owns or has been explicitly granted. The refusal is `denied: permission_denied: write_package`, and it arrives AFTER the full build, which is the expensive place to find out. **Granting an existing package is UI-only**—Package settings, Manage Actions access, add `feralcreative/routeloop` with the Write role; there is no REST endpoint for it (`/user/packages/container/routeloop/repositories` is a 404). The `org.opencontainers.image.source` LABEL in the `Dockerfile` is what stops the NEXT package needing that step, because it links the package to the repository on push—but it cannot retroactively link one that already exists.
- **STAGE DEPLOYS ITSELF ON EVERY PUSH TO `main`; PROD IS A BUTTON AND MUST STAY ONE.** Ziad's call, 2026-08-29. `.github/workflows/deploy-stage.yml` carries `push: branches: [main]`, `deploy-prod.yml` carries `workflow_dispatch` and nothing else, and **adding a `push:` trigger to the prod one is the change to refuse**—three riders hold real accounts, so the thing standing between a merge and a production deploy is a person deciding to deploy. **The reason both exist at all is BANDWIDTH rather than ceremony**: the deploy builds the image and pushes a few hundred MB to GHCR, so run from a laptop that upload is on the laptop's uplink and run from a runner it costs nothing—which is the whole point on a bad connection, and why `prod.sh` from a terminal is now the fallback rather than the normal path. **The prod workflow takes no `ref` input on purpose**: `deploy.sh` refuses a prod deploy that is not on `main` and `actions/checkout` detaches HEAD for anything that is not a branch, so a tag would be rejected after a full five-minute build. **Rolling back is not a deploy**—`deploy-utils.sh cutover blue|green`, about ten seconds. Neither workflow has an approval gate, deliberately: a required reviewer on a solo repo is the author approving himself, and what stops a stranger dispatching one is write access to the repository.
- **A WORKFLOW MUST NOT DOWNLOAD ANYTHING INTO THE CHECKOUT, BECAUSE THE CLEAN-TREE GATE IS PROD-ONLY.** Both deploy workflows install cloudflared, and a bare `curl -o cloudflared.deb` puts it in the repo root where `git status --porcelain` reports it as untracked. `deploy.sh` refuses a dirty tree—but only for prod—so this passed on stage every single time and failed the FIRST prod run with "Working tree is dirty" on a tree `actions/checkout` had created seconds earlier. It is `$RUNNER_TEMP` now. **The general shape to watch for: anything gated on `DEPLOY_ENV = prod` is untested by every stage deploy**, so the prod path's first run is its first test however green stage has been.
- **`DEPLOY_SKIP_ENV=1` MAKES A DEPLOY VERIFY THE SERVER'S `.env` INSTEAD OF WRITING IT, AND THE VERIFICATION IS THE LOAD-BEARING HALF.** It exists so CI never reads an application secret: `deploy.sh` normally composes the remote `.env` from ~25 values in the local one, and a workflow doing that would need every one as an Actions secret. Skipping the write WITHOUT checking would ship a release whose new required key is simply absent—and that failure is silent, because the container starts and passes its healthcheck regardless. So `REMOTE_ENV_KEYS` names every key ONCE, the writer fills those in and the verifier checks for exactly those; two lists would drift the first time anyone added a variable. `IMAGE_NAME`, `APP_VERSION` and `BUILD_SHA` are exempt because the deploy is their source and rewrites them in place. `deploy-utils.sh push-env` is the other half—**a new key has to be pushed BEFORE the release that needs it**, or that release's CI deploy correctly refuses. **THE SKIP HAS TO REACH THE COMPOSITION, NOT ONLY THE WRITE.** It did not until 2026-08-30: the remote `.env` was built unconditionally and only the `ssh` that sends it was guarded, so under `set -u` the first name with no `:-` default—`GMAPS_KEY`—killed every CI deploy thirteen seconds in. Defaulting them all is the wrong fix, because that composes a file of empty strings and leaves one `if` as the only thing between it and the server. It stayed invisible while every CI run was failing further up, and surfaced the moment stage started deploying itself.
- **THERE IS A DEPLOY LOCK NOW, IT LIVES ON THE NAS, AND IT IS A `mkdir`.** On the NAS because the two racers are different machines—a workflow and a terminal—so a local `flock` would see neither. A `mkdir` because it is atomic, where test-then-touch has a window that hands the lock to both. Taken before the BUILD rather than before the cutover, so the loser finds out in a second instead of after a five-minute build. **It never expires on its own**: a self-expiring lock expires during the slowest deploy you ever run, which is exactly the one where a second deploy starting is worst. `deploy-utils.sh unlock` reports the holder before breaking it.
- **NEVER A BARE `docker-compose up -d` IN THE DEPLOY DIRECTORY, AND NEVER `--remove-orphans`.** The first would start both colors at once; the colors sit behind Compose profiles (`blue`, `green`, and `tools` for the migrator) so it currently cannot, and naming a profiled service explicitly still starts it, so the deploy is unaffected. The second would remove the pre-blue/green `routeloop` container, which is an orphan of this compose project by definition—removing it is a decision somebody makes on purpose, not a side effect of a flag.
- **THE TWO COLOR BLOCKS IN `docker-compose.prod.yml` ARE WRITTEN OUT IN FULL, AND A YAML ANCHOR MUST NOT BE USED TO SHARE THEM.** `<<: *app` merges TOP-LEVEL keys only, so an `environment:` in the second block REPLACES the anchored one wholesale rather than extending it—green would get `APP_COLOR` and nothing else. Given the length of that env list and how a missing `GOOGLE_CLIENT_SECRET` fails (silently, with no sign-in at all, on a container that passes its healthcheck), duplication a human can diff beats a merge rule that quietly drops keys. They must stay identical apart from the service name, `container_name`, `APP_COLOR` and `profiles`.
- **`DB_VOLUME_NAME` IS HARD-PINNED PER ENVIRONMENT, NOT DERIVED.** Ziad's call, 2026-08-27. Compose addresses a volume as `<COMPOSE_PROJECT_NAME>_db-data`, so a changed project name or a reshaped volume block makes it create a NEW EMPTY volume—Postgres initializes a fresh database into it, the container passes its healthcheck, and the deploy reports success while every rider's account is gone. Naming it explicitly turns that silent loss into a loud failure. The parameterized form `${COMPOSE_PROJECT_NAME}_db-data` reads tidier and pins nothing: it derives the name from the value most likely to be wrong.
- **NODE IS PID 1 IN THE CONTAINER, AND THAT LINE IS WHAT MAKES THE GRACEFUL SHUTDOWN REAL.** The `Dockerfile` ended with `CMD ["npm", "run", "start"]` until 2026-08-27, which put **npm** at PID 1 with node as its child and a `tsx` shim in between. npm's signal forwarding is historically unreliable, so SIGTERM could simply never arrive—and the failure is completely silent: `src/shutdown.ts` becomes dead code, every deploy hard-kills whatever is in flight, and every log line says the deploy worked. It is `CMD ["node", "--import", "tsx", "src/index.tsx"]` now. `node --import tsx` is verified working against the pinned `tsx ^4.19.2`, but **the signal half has only been verified locally, not in the container**: the acceptance test is `docker stop` on stage, confirming both that `[shutdown] SIGTERM received, draining` appears in the logs AND that the container exits in about a second rather than taking the full ten-second SIGKILL timeout. A fast exit with no log line means the signal is still being swallowed.
- **`/healthz` IS WHAT THE DEPLOY GATES ON, AND IT REPORTS THE BUILD FOR ONE REASON.** A 200 alone proves something is listening, and this project's recurring failure mode is the silent success—a `docker-compose up -d` that decides the service is up-to-date leaves the OLD container running, which answers a plain health probe exactly as happily as a new one. So the gate asserts the SHA it just pushed, and `--force-recreate` is what makes the new container actually exist. **A draining container answers 503 while it is still serving**, which is the point rather than a contradiction: it must finish what it has and be sent nothing new. It is registered as the FIRST route in `index.tsx`, above `LEGACY_HOSTS` (a probe must never be answered with a 301) and above `withSession` (a health check that takes a session lookup is measuring the wrong thing).
- **The zip download route is registered ahead of the generic `:format` route on purpose** in `src/index.tsx`. Registered after it, the generic route swallows `/zip/gpx` and answers with a plain GPX. Observed, not theorized.
- **The `routeloop_` filename marker is load-bearing.** `parseExportName` returns `null` without it, so a rider's own `day-2.gpx` is never reinterpreted. Underscores separate fields and hyphens live inside one; do not simplify the separator. Dates are formatted and parsed in UTC because the roadbook renders `days.start_at` with `timeZone: 'UTC'`.
- **Two brand names are read where one is written, and that is permanent.** `READ_MARKERS` in `src/maps/filename.ts` accepts `tankbag_` alongside `routeloop_`, `COMPOUND_EXTS` accepts `.tankbag.json`, `nativeVersion()` in `src/maps/export.ts` reads either version key, and `/api/public/maps/:slug/tankbag.json` is still routed. None of that is leftover debris from the rename—it is what keeps every file a rider already downloaded importable, and dropping it fails silently: the files still import, just stripped of the day order and dates that GPX and KML cannot carry internally. `public/js/filename.js` mirrors all of it. Tidying any of it away needs a decision, not a cleanup pass.
- **A filename is not a format.** It carries four fields and the date is the one doing the work, because **none of the four lossy formats writes a day's clock**—not GPX or KML, which have nowhere to put one, and not GeoJSON, which has arbitrary `properties` and could. That last one is a decision as of 2026-08-27 and not an oversight: the four agreeing is what keeps a ride's date independent of which format it was exported as. `test/fidelity.test.ts` asserts the row. Resist adding roles, colors or dwell to the filename.
- **The pre-commit tightener rewrites em dashes in test fixtures too.** `test/em-dashes.test.ts` was once committed comparing strings to themselves because of it.
- **A COLOR TOKEN IS A `var()` NOW, AND ANYTHING THAT READS THE SCSS TO FIND A COLOR IS BROKEN BY THAT.** `/brand` parses `_tokens.scss` and decides "is this a color" with a regex, and the theme engine turned every token in that file into `var(--x)`—so the page went from every color the app defines to none of them, on a branch whose entire subject was color, and nothing failed. The values live in the compiled stylesheet; `parsePalette()` in `src/views/tokens.ts` reads them back out of the `:root` block. Reading the BUILD rather than re-deriving the palette in TypeScript is deliberate: a second implementation of the color math would disagree eventually, and the disagreement would look like a design decision.
- **`.page-tabs` / `.page-tab` / `.page-tabpanel` live in `_chrome.scss`, not `_dashboard.scss`.** They were named as generic classes from the start and are on two surfaces now—the dashboard's ride lists and the riders screen—so they moved on 2026-08-29. The behavior was always shared: `public/js/tabs.js`, which the builder's panel strip also uses with its own CSS, because a 380px drawer and a page-width strip want different metrics.
- **`ul.cards` is the generic white-row list; `.ride-cards` is the ride grid.** They are two classes because they are two things—`/admin`'s rider roster and the survey summary are built on the first, and turning it into a picture grid gave the roster a column of empty frames. A ride list wants `.ride-cards`, with `.ride-cards--dense` where the list is not the page's whole job.
- **`contrast()` in `src/views/tokens.ts` must read `rgb()` as well as hex.** Sass emits a hex for an authored literal but `rgb(60%, 40.47%, 0%)` for anything `color.adjust()` produced, which is every derived token in the palette—so a hex-only reader silently skips exactly the tokens most likely to have a contrast problem. It also knows `black` and `white`, because Sass writes the shortest form and a derivation clamped at either end of the lightness scale arrives as a keyword.
- **`color.adjust()` does not clamp at zero.** Darkening a color past its own lightness emits `hsl(…, -3.04%)`, which is out of range, which a browser clamps to black—so the token silently resolves to black and the build succeeds. `-adj()` in `_palette.scss` clamps for that reason.
- **A derivation whose job is to be READ takes an absolute lightness, not a relative step.** A step assumes the base sits where the default palette put it, and a theme that moves the base moves the step with it: the high-contrast theme lightened `$warning`, correctly, because it is a black-legend field—and `$pending`, which was `-20%` from it, came out at **2.24:1 on white**. Amber text was least legible in the theme named for legibility. `-tone()` is the fix.
- **There is no global `border-box` reset in `style/`.** Every fixed-size box sets its own `box-sizing`, so a new one that forgets has its `width` and `aspect-ratio` describe the CONTENT box while padding sits outside them—it renders wider than it declares and nothing warns. It cost a day on `.btn-stop`, where the symptom was a legend that would not wrap at any viewport.
- **Never put a raw U+00A0 in source.** It is invisible in a diff and in most editors, so a stray one is unreviewable and a stripped one is undetectable. Write `&nbsp;` in JSX text, `'\u00a0'` in a string literal. Note also that the em-dash tightener counts a non-breaking space as whitespace on both sides of a dash, so binding a pair across an em dash is silently undone by the pre-commit hook.
- **A broad `npx prettier --write "src/**/*.ts"` produces about 22 files of collateral.** The committed tree is not prettier-clean under the current config, so a wide glob reformats files you never touched—line wraps collapsed, arrow-body parens added—and sweeps them into your commit. Scope the glob to the files you actually changed.
- **Never interpolate a JS array into a tagged `sql` template.** Drizzle expands the array into a tuple, so a hand-written `= any(...)` over one comes out as `any(($2, $3, $4))`, which is not valid SQL. Use `inArray`. There is no type error and no test failure—it fails at runtime, on the first render of whatever page needed it.
- **An email may not put `#` before a number.** `test/email-theme.test.ts` scans rendered HTML for `#` followed by 3–6 hex characters to catch a template inventing a color, and every decimal digit is also a hex digit, so "Report #1042" fails the guard. The scanner cannot be narrowed to attribute values either: `shell.tsx` puts most colors in `<style>` blocks. Write "Report 1042".
- **`test/emails.test.ts` requires every link in a template's HTML arm to appear in its text arm.** A text-only client silently losing a link is the failure the two-arm contract exists to prevent.
- **Feedback attachment bytes are counted in `feedback_attachments.bytes` and nowhere else.** They must stay out of `rides.size_bytes` and `users.used_bytes`—an attachment is not ride data, must not eat a rider's quota, and a fourth byte column in that generated expression would corrupt quota accounting on every ride delete.
- **The queue's moderation handler writes only the fields it is given.** That is why it is several small forms rather than one wide one: a single form carrying every field would blank whatever the owner had not retyped. Keep `moderate()` field-optional if you touch it.
- **`utils/` is not in `tsconfig.json`.** `npm run typecheck` does not cover it, and a bad import there fails only at runtime. Check a `utils/` change by hand:

  ```bash
  npx tsc --noEmit --strict --target ES2022 --module ESNext --moduleResolution Bundler \
    --types node --esModuleInterop --skipLibCheck utils/seed-demo-rides.ts
  ```

- **`test/` is in `tsconfig.json` on purpose.** Vitest transpiles without type-checking, so removing it hides fixture drift. Keep it there.
- **The builder's snapshot shares what is never mutated in place, and that set changes.** `leg.geometry` is shared by reference because it is always replaced wholesale; `point.roles` must be copied because `splice()` mutates it, and `point.details` joins it for the same reason—the field editor assigns into that object one field at a time, and `details.links` is an array it pushes to. `leg.viaPoints` moved between the two groups the day drag-to-shape shipped and nothing failed loudly. Re-check whenever you add an edit-in-place feature.
- **SORTABLE REPORTS TWO PAIRS OF INDICES AND ONLY ONE PAIR MEANS A POINT.** `oldIndex`/`newIndex` count EVERY child of the list; `oldDraggableIndex`/`newDraggableIndex` count only children matching `draggable`. A point list renders an `.insert-slot` hairline above every row plus a trailing `.add-row`, so it holds **2n+1 children for n points** and the raw index runs at roughly double the one `day.points` is addressed by. Reading the raw pair was #166, live from 2026-08-24—when the insert slots landed nine days after the arithmetic—to 2026-08-27, and it failed two ways at once: a drag whose doubled index clamped back onto its own position **did nothing and never marked the ride dirty**, so the row snapped back on the next render with no save attempted, and every other drag **overshot by about double and saved that**. It was invisible by eye because `orderedRows` renumbers stops 1..n by POSITION on every render, so the list reads 1, 2, 3… however wrong the order is—only the place names give it away. `#day-list` is the one handler where the raw pair is still correct, and only because it holds nothing but `.day-section` children; put any sibling between them and it breaks the same silent way.
- **SortableJS `filter` cancels the click that focuses an input, and `preventOnFilter: false` is what stops it.** The option defaults to TRUE, so Sortable calls `preventDefault()` on any pointerdown landing inside a filtered element—and the default action being canceled is the one that moves focus. Each day's `.add-row` is filtered so a drag cannot start on it, which silently made its search field unclickable: it could be tabbed to and typed in, but a click left focus on `<body>`. Shipped that way and reported as "I can't click into the search"; fixed 2026-08-22. `filter` still blocks the drag either way—that check does not need the event canceled.
- **Empty days are dropped at save time.** The API requires at least one stop per day, so `payload()` in `builder.js` filters days with no points rather than failing the whole ride. The stop is guaranteed by `addPoint()` promoting the first point of every day; the schema still refuses a day of nothing but POIs, and the refine says so. Note the rule is no longer about routing—a day of nothing but POIs draws a complete road—but about the roadbook's numbered rows, the Maps hand-off, and somewhere for `start`/`finish` to live.
- **`ride.json` sends ONE ordered `points` array, the same shape as the builder payload and the native JSON.** It sent `stops` and `pois` as two arrays until 2026-08-24, deliberately, because the viewer draws markers and a timeline and never rendered points as a sequence. A POI joining the route ended that: `ride-time.js` walks the points and the legs together to build a day's schedule, and two arrays cannot tell it the order. `ride-time.js` and `twist.js` are shared by the builder and the viewer and now accept ONE shape—do not reintroduce a second, or the two surfaces will disagree about a ride's schedule.
- **Native JSON is format version 5, and versions 2, 3 and 4 still import.** `upgradeNativeRide` merges a pre-v4 file's `stops` and `pois` into one list, stops first, stamping each kind explicitly—a v3 stop must not fall through to the `poi` default. **v5 is the first bump that is not a rename:** a pre-v5 file holds `stops - 1` legs where a day now needs `points - 1`, so every day's legs are re-cut from its own track at every point (`relegDay` in `track-split.ts`) and the recorded riding time is spread across them by distance rather than zeroed. Nothing is re-routed and no coordinate is invented. The rider's ORDER is kept rather than re-derived—a v4 POI's place in the list was their own choice, so a point projecting behind its predecessor is clamped forward for a zero-length leg instead of being sorted. Riders have those files on disk and a backup that will not restore is not a backup.
- **The production database is precious, and the uptime is no longer free.** Three riders have had accounts on production since 2026-08-25, so a broken deploy is now visible to somebody rather than to nobody—that half of this rule changed, and the app is still not zero-downtime, although the gap is now seconds rather than a minute and a half—Phase 1 of [docs/zero-downtime-deploy.md](docs/zero-downtime-deploy.md) shipped 2026-08-27, so the database is no longer torn down and migrations run before the new code serves anything; Phase 2, blue/green behind Caddy, is still a proposal and nothing in it is built. Overwritten code costs approximately nothing, because the tree is in git. The rows are the opposite: `users` holds real outside signups, some active and some sitting at `status = 'pending'`, and those records are not reconstructable. Take a `db-backup` before anything that could touch the volume, and treat `docker compose down -v`, a `$DOMAIN` change, and a stale-volume adoption as the three ways to lose them. Nothing in the app prunes a pending user, so the only risk is operational.
- **THE BUILDER PANEL IS THREE TABS, and the Riders one is the only place a subgroup id and a subgroup uid meet.** Ziad's call, 2026-08-26: Routes, Groups and Riders, with the ride's description and visibility above the strip and Delete below all three. Everything in `builder.js` holds a subgroup by **uid**, because the client mints those and `reconcileSubgroups` matches on them; `ride_members.subgroup_id` is a numeric **id** that does not exist until the ride has been saved. So the Riders tab's group picker builds its options from `/api/rides/:id/riders`—the SERVER's list, which carries both—and never from `state.meta.subgroups`. **The consequence to state rather than treat as a bug: a group added since the last save cannot be assigned to anybody**, and the tab says so in a line rather than leaving it silently missing from the picker. `sameGroupUids()` is what re-reads the tab when a save changes the set.
- **A DAY'S CLOCK IS A WALL CLOCK AT THE DEPARTURE POINT, CARRIED AS UTC.** Ziad's call, 2026-08-24: a time is a time is a time at the departure point. A rider who plans a 9am departure means 9am where the bike is—whether they planned it from home, from a hotel two states over, or from London a fortnight before flying out—so **nothing in this app converts a day's clock into anyone's local time, ever**. `public/js/day-clock.js` is the only place the conversion between that value and an `<input type="datetime-local">` happens, and `point_details.check_in_at`/`check_out_at` follow the same rule. Three consequences to state rather than treat as bugs: **the columns stay `timestamptz` although the values are naive**, because node-postgres parses a real `timestamp` in the PROCESS's zone and the app would then depend on `TZ` (measured, not assumed—a stored `09:00` reads back `16:00Z` on a Pacific machine); **every surface reads it with `timeZone: 'UTC'`**, which is now correct rather than the workaround it was; and **a rider in London planning a California ride types California times**, because the field has no zone of its own to show them. Do not "fix" the UTC away.
- **Be careful with how a migration runs, not about whether to do one.** Deferring a schema change out of caution once shipped imports that destroyed multi-day structure.
- **A data migration is not always a SQL file, and the ones that are not fail silently.** The 2026-08-24 leg-count change needed no schema change at all—`route_legs` never referenced a stop—so nothing rejects a day still carrying `stops - 1` legs. Opening one in the builder fills the gap with straight placeholder legs drawn out to each POI and back, on the first edit, with nothing raised. `utils/split-imported-legs.ts` is the fix and it has to be RUN; `--dry-run` first, and a `db-backup` before it either way. **The wall-clock change the same day is the second of these**: nothing rejects a `start_at` still holding an instant, it just prints hours out, and `utils/shift-days-to-wall-clock.ts --zone <IANA>` un-applies the offset. That one is **not idempotent**—a shifted row is indistinguishable from an unshifted one—so it runs once, after a backup.

### The CI deploy's credentials live in GitHub, not in `.env`

Five repository secrets, set 2026-08-29: `NAS_SSH_HOSTNAME`, `NAS_SSH_KEY`, `NAS_SSH_KNOWN_HOSTS`, `CF_ACCESS_CLIENT_ID`, `CF_ACCESS_CLIENT_SECRET`. **No application secret is among them, and that is the design**—see `DEPLOY_SKIP_ENV` above.

**THE ACCESS SERVICE TOKEN EXPIRES 2027-08-29, AND THE FAILURE WILL NOT LOOK LIKE AN EXPIRY.** `routeloop-ci-deploy` was minted with a one-year duration. When it lapses, Cloudflare Access starts refusing the runner and the symptom is an SSH step that hangs or fails to connect—which reads as a network problem, a NAS problem, or a tunnel problem long before anyone thinks of a date. **If a CI deploy fails at the SSH step on or after that date, check this first.** Rotating it is: create a new service token, set the two repository secrets, repoint the Access policy's `service_token` include at the new id.

**`NAS_SSH_KNOWN_HOSTS` MUST BE GENERATED WITH THE PORT, AND THE WRONG ONE FAILS IDENTICALLY TO A WRONG KEY.** `ssh` looks a host up in `known_hosts` under the name AND port it was given, and port 33725 is not 22, so the key is BRACKETED—`[nas.feralcreative.co]:33725`. An entry from a portless `ssh-keyscan nas.feralcreative.co` is filed under the bare hostname, never matches, and produces a bare `Host key verification failed.` that says nothing about why. Regenerate it as `ssh-keyscan -p 33725 nas.feralcreative.co`, or lift the entry your own machine already trusts with `ssh-keygen -F '[nas.feralcreative.co]:33725' -f ~/.ssh/known_hosts`. A host public key is not a secret; it is a repository secret only because it is a value CI needs. `check_ssh_reachable()` in `lib.sh` names this case explicitly now, because the first time it happened the deploy reported a held lock instead.

**Cloudflare's client secret is returned exactly once**, at creation. It exists in GitHub and nowhere else; there is no way to read it back out of Cloudflare. Losing it means minting a new token, not recovering this one.

**THE NAS'S SSH PORT 33725 IS OPEN TO THE PUBLIC INTERNET AND STAYS THAT WAY.** Ziad's call, 2026-08-29: he uses it. `nas.feralcreative.co` is an UNPROXIED CNAME to a Synology DDNS name, so it bypasses Cloudflare entirely, and the tunnel route added for CI is a second path rather than a replacement. Do not keep proposing that it be closed—the decision is recorded, and the tunnel was worth building anyway because it is what CI uses. Note the consequence for anyone reasoning about the deploy: **the NAS is NOT unreachable from the internet**, so an argument that begins "CI cannot reach the NAS without a tunnel" is false and was false when it was first made here.

The deploy writes the server's `.env` from an explicit allow-list in `utils/deploy/deploy.sh`. A new required key that is not added to that list reaches no environment, and the container still starts and passes its healthcheck.

## Commit and PR conventions

- **An audible gets its issue written AFTER the fact, and closed immediately.** Ziad's call, 2026-08-24. Work here is often raised out loud and built the same day, and stopping to file a ticket first is exactly the friction that makes it not happen—so the issue is written when the work is done, describing what was decided and why, and closed in the same breath. **It is not optional bookkeeping**: the tracker is what answers "why is it like this" a year from now, and twenty-three issues had to be reconstructed on 2026-08-24 because nobody had been doing it. One issue per coherent unit of work, labeled as if it had been filed up front.
- Conventional Commits: `type(scope): subject`, imperative mood. Types in use: `feat`, `fix`, `refactor`, `docs`, `chore`, `style`, `test`. Scope optional, welcome when it clarifies.
- Branch as `type/kebab-subject`—`feat/trip-timeline-slider`, `fix/multi-track-import`.
- **BRANCH BY AREA, NOT BY ISSUE, AND PREFER FEWER LARGER PRs.** Ziad's call, 2026-08-24. Every issue carries exactly one `area:` label (a few carry two where the work genuinely straddles), and an area is the unit of work: pick one, branch, clear what you can of `gh issue list --label area:<name>`, open one PR, move on. **Group liberally**—a hyper-granular history of one-issue branches is explicitly not wanted.
